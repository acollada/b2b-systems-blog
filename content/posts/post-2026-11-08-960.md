# Optimización de consultas SQL y gestión de índices en ERPs B2B

Los ERP (Enterprise Resource Planning) B2B suelen manejar volúmenes de datos enormes: órdenes de compra, facturas, inventario, movimientos de contabilidad, etc. La calidad de las consultas y la estructura de los índices son críticos para garantizar un rendimiento aceptable en producción.  
En este artículo se cubren los requisitos previos, un paso a paso de implementación, un bloque de código de ejemplo y buenas prácticas con errores comunes a evitar.

> **Nota**: Este material se centra en bases de datos relacionales de uso común en ERPs (SQL Server, PostgreSQL, Oracle, MySQL). Los conceptos son aplicables a otras plataformas con pequeñas diferencias sintácticas.

---

## 1. Requisitos previos y contexto técnico

| Área | Requisitos | Herramientas recomendadas |
|------|------------|---------------------------|
| **Hardware** | CPU multi‑core, RAM ≥ 16 GB, SSDs NVMe | `top`, `htop`, `iostat`, `vmstat` |
| **Base de datos** | Versiones 12+ (SQL Server 2019, PostgreSQL 13+, Oracle 19c, MySQL 8.0) | `sqlcmd`, `psql`, `sqlplus`, `mysql` |
| **Conocimiento de SQL** | SELECT, JOIN, GROUP BY, subqueries, CTEs | `SQL Server Management Studio`, `pgAdmin`, `Oracle SQL Developer`, `DataGrip` |
| **Herramientas de monitoreo** | DMVs (Dynamic Management Views), pg_stat, AWR, Oracle Enterprise Manager | `sys.dm_exec_query_stats`, `pg_stat_activity`, `AWR` |
| **Herramientas de profiling** | SQL Profiler, pgBadger, Oracle SQL Developer Profiler | `sqlcmd -Q "SET STATISTICS PROFILE ON;"`, `pgBadger` |
| **Control de versiones** | Git, SVN | `git`, `svn` |
| **Automatización** | PowerShell, Bash, Python | `Invoke-Sqlcmd`, `psql -f`, `psycopg2` |

### Contexto típico de un ERP B2B

1. **Múltiples módulos**: Ventas, compras, finanzas, logística, CRM, etc.  
2. **Transacciones masivas**: Inserción de cientos de líneas de factura por día.  
3. **Consultas ad‑hoc**: Informes de cumplimiento, auditorías, KPIs.  
4. **Usuarios concurrentes**: Varias decenas de usuarios en tiempo real.  
5. **Requisitos de SLA**: Tiempo de respuesta < 2 s para la mayoría de consultas.  

La optimización debe considerarse **en el diseño de la base de datos** (normalización/denormalización, particiones) y **en la capa de aplicación** (caching, pre‑compilación de queries).

## 2. Paso a paso de implementación

1. **Identificar consultas críticas**  
   - Ejecuta `SELECT * FROM sys.dm_exec_query_stats ORDER BY total_elapsed_time DESC` (SQL Server) o `SELECT * FROM pg_stat_statements ORDER BY total_time DESC` (PostgreSQL).  
   - Exporta las queries con más tiempo de CPU y I/O.  
   - Prioriza aquellas con > 10 000 ejecuciones/día o que son usadas por usuarios finales.

2. **Revisar planes de ejecución**  
   - Genera `SET SHOWPLAN_XML ON;` (SQL Server) o `EXPLAIN (ANALYZE, BUFFERS)`.  
   - Busca `Table Scan`, `Index Scan` con alto costo, `Hash Match`, `Sort` innecesarios.  
   - Identifica los índices que realmente se usan y los que son “dead”.

3. **Analizar cardinalidad y estadísticas**  
   - Actualiza estadísticas: `UPDATE STATISTICS <tabla> WITH FULLSCAN` (SQL Server).  
   - Verifica la calidad de estadísticas con `DBCC SHOW_STATISTICS`.  
   - Si la cardinalidad está muy desfasada, considera `REBUILD` o `REORGANIZE` de índices.

4. **Diseñar o ajustar índices**  
   - **Índices compuestos**: incluye columnas en WHERE + JOIN + ORDER BY.  
   - **Índices filtrados** (SQL Server) o **partial indexes** (PostgreSQL) para tablas con valores muy poco frecuentes.  
   - Evita índices redundantes: si `idx_customer_name` y `idx_customer_name_email` cubren lo mismo, elimina el menor.  
   - Añade columnas de cobertura en el índice (`INCLUDE` en SQL Server, `INCLUDE` en MySQL 8.0).

5. **Optimizar consultas**  
   - Reescribe sub‑queries en CTEs o `JOIN`s cuando sea más eficiente.  
   - Utiliza `OPTION (RECOMPILE)` solo cuando sea necesario.  
   - Evita funciones en columnas de filtro (`WHERE YEAR(date_col) = 2024` → `WHERE date_col >= '2024-01-01' AND date_col < '2025-01-01'`).  
   - Usa `WITH (NOLOCK)` solo cuando la consistencia estricta no sea crítica.

6. **Particionar tablas**  
   - Para tablas históricas (facturas, órdenes), crea particiones por rango de fecha (`PARTITION BY RANGE (fecha)` en SQL Server).  
   - Configura `FILEGROUPS` y `PARTITION SCHEMES`.  
   - Asegúrate de que las consultas filtren por la columna de partición.

7. **Revisar configuración del motor**  
   - `max degree of parallelism` (SQL Server) o `max_parallel_workers_per_gather` (PostgreSQL).  
   - Ajusta `work_mem` en PostgreSQL o `max server memory` en SQL Server.  
   - Habilita `Query Store` (SQL Server) para seguimiento histórico.

8. **Automatizar**  
   - Programa tareas nightly de `DBCC UPDATEUSAGE`, `sp_updatestats`, `REBUILD INDEXES`.  
   - Usa scripts de PowerShell/Bash para generar reportes de rendimiento.  
   - Integra alertas en sistemas de monitoreo (Prometheus, Grafana).

9. **Validar cambios**  
   - Ejecuta pruebas de carga con `JMeter` o `LoadRunner`.  
   - Compara métricas de tiempo de respuesta y CPU antes/después.  
   - Verifica que el número de I/O se reduzca (monitor `iostat`).

10. **Documentar**  
    - Registra cada índice creado/alterado, su propósito y el impacto.  
    - Mantén un changelog de versiones de la base de datos.  
    - Actualiza la documentación de la capa de aplicación sobre cambios en la lógica de consultas.

## 3. Bloque de código de ejemplo comentado

```sql
-- Ejemplo: Optimización de la consulta de facturas pendientes
-- Tabla: Facturas (Facturas)
-- Columnas clave: Id, ClienteId, FechaEmision, Estado, Total

-- 1. Índice compuesto con columnas de filtro y orden
CREATE INDEX IX_Facturas_Pendientes
ON Facturas (ClienteId, FechaEmision DESC)
INCLUDE (Estado, Total);   -- columnas de cobertura para evitar look‑ups

-- 2. Consulta original (table scan)
-- SELECT * FROM Facturas
-- WHERE ClienteId = 123
--   AND Estado = 'PENDIENTE'
-- ORDER BY FechaEmision DESC
-- LIMIT 10;

-- 3. Consulta optimizada (index seek + key lookup)
SELECT TOP 10
       Id,
       ClienteId,
       FechaEmision,
       Estado,
       Total
FROM Facturas
WHERE ClienteId = 123
  AND Estado = 'PENDIENTE'
ORDER BY FechaEmision DESC;
```

**Explicación**  
- El índice `IX_Facturas_Pendientes` cubre la cláusula `WHERE` (`ClienteId`, `Estado`) y la columna de orden (`FechaEmision`).  
- La cláusula `INCLUDE` agrega `Total` al índice, permitiendo que la consulta sea **cobertura completa** y evita un segundo acceso a la tabla.  
- Con este índice, el plan de ejecución mostrará un `Index Seek` seguido de un `Index Scan` mínimo, reduciendo el I/O.

## 4. Buenas prácticas y errores comunes a evitar

### Buenas prácticas

| Área | Recomendación | Por qué |
|------|---------------|---------|
| **Diseño de índices** | Usa índices compuestos con columnas de filtro y orden. | Reduce el número de accesos a disco. |
| **Cobertura** | Incluye columnas no clave que se usan en SELECT. | Evita look‑ups adicionales. |
| **Particiones** | Particiona por rango de fechas en tablas históricas. | Facilita la eliminación de datos antiguos y mejora el rendimiento de consultas filtradas por fecha. |
| **Mantenimiento** | Programa `REBUILD`/`REORGANIZE` según fragmentation > 30 %. | Mantiene índices compactos y eficientes. |
| **Actualización de estadísticas** | Ejecuta `UPDATE STATISTICS` nightly o cuando la cardinalidad cambie > 10 %. | Garantiza planes de ejecución precisos. |
| **Monitoreo continuo** | Habilita Query Store / AWR y revisa cada 24 h. | Detecta regresiones de rendimiento. |
| **Reescritura de consultas** | Evita funciones en columnas de filtro, usa `BETWEEN` y `>= / <`. | Evita la pérdida del índice. |
| **Seguridad** | Mantén el principio de mínimo privilegio en las vistas y stored procedures. | Reduce la exposición de datos sensibles. |

### Errores comunes a evitar

| Error | Impacto | Cómo prevenir |
|-------|---------|---------------|
| **Índices redundantes** | Aumento de I/O y espacio en disco | Revisa `sys.dm_db_index_usage_stats` para detectar índices no usados. |
| **Índices con columnas de alta cardinalidad en el último nivel** | Se vuelve similar a un `FULL SCAN` | Ordena columnas en el índice de menor a mayor cardinalidad. |
| **Actualización de estadísticas poco frecuente** | Planes obsoletos, tiempos de ejecución altos | Automatiza actualizaciones o usa `AUTO_UPDATE_STATISTICS`. |
| **Ignorar la fragmentación** | Índices fragmentados > 30 % ralentizan las búsquedas | Ejecuta `ALTER INDEX ... REORGANIZE` o `REBUILD`. |
| **Uso excesivo de `NOLOCK`** | Lectura sucia, inconsistencias | Solo en reportes de lectura que toleren inexactitud. |
| **No revisar la cardinalidad en filtros** | Índice no utilizado | Usa `EXPLAIN` para ver si el índice es ignorado. |
| **Particiones sin key de partición** | Consulta de todas las particiones | Asegúrate de que la cláusula `WHERE` incluya la columna de partición. |
| **Cambios de esquema sin pruebas** | Pérdida de rendimiento inesperada | Ejecuta pruebas de carga y compara métricas. |

---

## Conclusión

La optimización de consultas SQL y la gestión de índices en ERPs B2B es un proceso iterativo que combina análisis de rendimiento, diseño cuidadoso de índices, mantenimiento periódico y monitoreo constante. Siguiendo el flujo de trabajo paso a paso, aplicando buenas prácticas y evitando los errores comunes, se logra un sistema más robusto, con tiempos de respuesta consistentes y una mejor experiencia de usuario para los procesos críticos del negocio.
