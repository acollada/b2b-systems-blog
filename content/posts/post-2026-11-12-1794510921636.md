# Optimización de consultas masivas y prevención de bloqueos en tablas transaccionales de Business Central  

> **Objetivo:**  Proveer una guía técnica avanzada para diseñar, implementar y mantener procesos de lectura/escritura masiva en Microsoft Dynamics 365 Business Central (AL) que minimicen los bloqueos de tabla y maximicen el rendimiento en entornos de alta concurrencia.

---  

## 1. Requisitos previos, contexto técnico y arquitectura en Business Central  

| Área | Detalle |
|------|---------|
| **Versión mínima** | Business Central 2022 Release Wave 2 (o superior). Se recomienda estar en la última versión para aprovechar mejoras de *Query* y *ExecuteQuery*. |
| **Entorno de desarrollo** | Visual Studio Code con la extensión **AL Language** y conexión a un **sandbox** o **dev** de Business Central. |
| **Base de datos subyacente** | Azure SQL Database (o SQL Server on‑prem). Conocer la configuración de **Read‑Committed Snapshot Isolation (RCSI)** y **Lock Escalation** es esencial. |
| **Permisos** | Necesario el rol **SUPER** o **Developer** y permisos de **ALTER** sobre objetos de tabla y código. |
| **Conceptos clave** | - **Record**, **RecordRef**, **Query**, **DataItem**, **TempTable**.<br>- **SetCurrentKey**, **SetRange**, **SetFilter**, **SetAscending/SetDescending**.<br>- **LockTable**, **ReadIsolation**, **Commit/Transaction**.<br>- **BatchSize** y **Chunking** para procesar grandes volúmenes. |
| **Arquitectura típica** | 1. **Front‑end** (Web/Client) → 2. **Service Tier (Azure Functions / API)** → 3. **SQL Engine**. Cada capa puede introducir latencia y bloqueos si no se controla la granularidad de la transacción. |
| **Patrones recomendados** | - **Read‑only**: usar `ReadIsolation := IsolationLevel::ReadCommitted` y evitar `FOR UPDATE`.<br>- **Write‑only**: agrupar cambios en lotes y ejecutar `COMMIT` después de cada lote.<br>- **Hybrid**: leer en modo *snapshot* y aplicar cambios en una segunda fase (pattern “Read‑Process‑Write”). |

---

## 2. Paso a paso de implementación en AL  

A continuación se describe la metodología paso a paso para crear una rutina de procesamiento masivo que:

1. **Lee** registros de una tabla transaccional grande (ej.: `Sales Header`).  
2. **Aplica** lógica de negocio (p. ej., cálculo de descuentos).  
3. **Actualiza** los registros sin bloquear toda la tabla y con un **commit** periódico.  

> **Nota:** Cada paso incluye consideraciones de bloqueo y rendimiento.

### Paso 1 – Definir parámetros de control  

```al
procedure ProcessSalesHeaders(BatchSize: Integer; MaxRecords: Integer)
```

- `BatchSize` = número de filas a procesar antes de `COMMIT`.  
- `MaxRecords` = límite máximo de registros a procesar en la ejecución (útil para pruebas).  

### Paso 2 – Preparar el `Record` con índices óptimos  

```al
    var
        SalesHeader: Record "Sales Header";
        RecCount: Integer;
        Processed: Integer;
```

1. **Seleccionar la clave primaria** (o una clave alternativa que reduzca el rango).  
   ```al
   SalesHeader.SetCurrentKey("Document Type", "No.");
   SalesHeader.SetAscending("Document Type", true);
   SalesHeader.SetAscending("No.", true);
   ```
2. **Aplicar filtros** para limitar el conjunto (por ejemplo, sólo facturas sin procesar).  
   ```al
   SalesHeader.SetRange("Document Type", SalesHeader."Document Type"::Invoice);
   SalesHeader.SetFilter("Processed", '%1', false);
   ```

### Paso 3 – Abrir la tabla en modo *Read‑Only* y desactivar bloqueos innecesarios  

```al
    SalesHeader.ReadIsolation := IsolationLevel::ReadCommitted;
    // Evita bloqueos de escritura mientras solo leemos
    // No se usa `LOCKTABLE` aquí.
```

### Paso 4 – Loop principal con control de lotes  

```al
    RecCount := 0;
    Processed := 0;
    if SalesHeader.FindSet() then begin
        repeat
            RecCount += 1;

            // ---------- Lógica de negocio ----------
            // (Ejemplo: aplicar descuento si el total supera un umbral)
            if SalesHeader."Amount Including VAT" > 10000 then begin
                SalesHeader."Discount %". := 5;
                // Marcar como procesado para evitar re‑procesamiento
                SalesHeader."Processed" := true;
                // Guardar cambios en modo *Update* sin bloquear otros registros
                SalesHeader.Modify(true); // true → SkipCheckSecurity
            end;

            // ---------- Commit por lotes ----------
            if RecCount MOD BatchSize = 0 then begin
                COMMIT; // Libera los locks de los registros ya procesados
                // Opcional: registrar progreso en una tabla de log
                Processed += BatchSize;
                // Reiniciar contadores de cambios internos (si fuera necesario)
            end;

            // ---------- Límite de ejecución ----------
            if (MaxRecords > 0) and (RecCount >= MaxRecords) then
                exit;
        until SalesHeader.Next() = 0;
    end;
    // Commit final para los registros restantes
    COMMIT;
```

### Paso 5 – Manejo de errores y rollback parcial  

```al
    // En caso de excepción, revertir cambios del lote actual
    try
        // … (código del bucle)
    on Error do begin
        // Deshacer solo el lote actual, no todo el proceso
        ROLLBACK;
        // Opcional: registrar el error y continuar con el siguiente lote
        // (re‑intentar o marcar el registro como "Error")
    end;
```

### Paso 6 – Exponer la rutina como **Codeunit** o **API**  

```al
codeunit 50100 "Sales Header Bulk Processor"
{
    procedure RunProcessing()
    begin
        // Parámetros de ejemplo: 500 registros por commit, sin límite máximo
        ProcessSalesHeaders(500, 0);
    end;
}
```
