# Patrones de diseño y control transaccional robusto en extensiones de **Microsoft Dynamics 365 Business Central** (AL)

> **Objetivo**: Proveer una guía técnica avanzada para estructurar extensiones de Business Central con patrones de diseño probados y un manejo de transacciones seguro, manteniendo alta performance y escalabilidad.  
> **Audiencia**: Desarrolladores AL con experiencia en C/AL y conocimientos básicos de arquitectura de Business Central.

---  

## 1️⃣ Requisitos previos, contexto técnico y arquitectura en Business Central  

| Área | Detalle |
|------|---------|
| **Entorno de desarrollo** | Visual Studio Code + extensión **AL Language** (versión ≥ 21.0). |
| **Versionado** | Al menos **BC 2022 Release Wave 2** (o superior) para disponer de `Savepoint`, `Commit`, `CancelTransaction` y `RunTrigger`. |
| **Licencia** | Sandbox o tenant de prueba con permisos de **Developer** y **Extension Management**. |
| **Conocimientos obligatorios** | - Modelo de datos de BC (tables, codeunits, pages).<br>- Principios de **AL** (variables, data types, `record`/`codeunit` lifecycle).<br>- Conceptos de **transactional scope** (`BeginTransaction`, `Commit`, `Rollback`). |
| **Arquitectura típica** | <br>![Arquitectura BC](https://i.imgur.com/placeholder.png) <br>1. **Presentation Layer** – Pages/Reports (UI).<br>2. **Application Layer** – Codeunits/Pages (lógica de negocio).<br>3. **Data Layer** – Tables + System Tables (persistencia).<br>4. **Integration Layer** – APIs, OData, Business Central Connectors. |
| **Patrones recomendados** | - **Service Layer** (codeunits como “services”).<br>- **Repository** (acceso a tablas encapsulado).<br>- **Unit of Work** (agrupación de cambios y control de commit).<br>- **Domain Events** (publishing/subscribing via `EventPublisher`/`EventSubscriber`).<br>- **Command‑Query Separation (CQS)** (separar operaciones de escritura y lectura). |
| **Control transaccional** | - **Implicit Transaction**: cada `INSERT/ MODIFY/ DELETE` se ejecuta dentro de la transacción implícita del servidor.<br>- **Explicit Transaction**: `BeginTransaction; …; Commit;` o `Savepoint` + `Rollback`. <br>- **Granularidad**: se recomienda **una única transacción por unidad de trabajo** (codeunit). |
| **Mecanismo de error** | - `Error` → lanza excepción y aborta la transacción.<br>- `Message` → notifica sin abortar.<br>- `try .. catch` → captura y gestiona excepciones sin perder la consistencia. |

---

## 2️⃣ Paso a paso de implementación en AL  

A continuación se describe la construcción de una solución que **crea una orden de venta y sus líneas** garantizando atomicidad, reutilizando patrones **Repository + Service + Unit of Work**.

1. **Crear la tabla de auditoría** (opcional, para logging).  
2. **Definir la interfaz `IRepository<T>`** que abstrae operaciones CRUD.  
3. **Implementar repositorios concretos** (`CustomerRepository`, `SalesHeaderRepository`, `SalesLineRepository`).  
4. **Construir el `UnitOfWork`** que agrupa los repositorios y controla la transacción.  
5. **Exponer un `Service`** (`SalesOrderService`) que orquesta la lógica de negocio.  
6. **Publicar eventos de dominio** (`OnSalesOrderCreated`).  
7. **Consumir el service desde una página o API** (ejemplo: `CreateSalesOrderPage`).  
8. **Añadir pruebas unitarias** (usando `TestPage` y `TestCodeunit`).  

> **Nota**: Cada paso incluye fragmentos de código que se detallan en la sección 3.

// 2️⃣ Interfaz genérica de repositorio
// ------------------------------------------------------------
interface IRepository<T>
{
    procedure Insert(var rec: T);
    procedure Modify(var rec: T);
    procedure Delete(var rec: T);
    procedure Get(var rec: T; primaryKey: Variant);
    procedure FindSet(var rec: T; filter: Text);
}

// ------------------------------------------------------------
// 3️⃣ Implementación concreta para Sales Header
// ------------------------------------------------------------
codeunit 50101 "SalesHeader Repository" implements IRepository<"Sales Header">
{
    // Inserta una cabecera de venta
    procedure Insert(var rec: Record "Sales Header")
    begin
        rec.Insert(true); // true → validar triggers
    end;

    // Modifica una cabecera de venta
    procedure Modify(var rec: Record "Sales Header")
    begin
        rec.Modify(true);
    end;

    // Elimina una cabecera de venta
    procedure Delete(var rec: Record "Sales Header")
    begin
        rec.Delete(true);
    end;

    // Obtiene una cabecera por No.
    procedure Get(var rec: Record "Sales Header"; primaryKey: Variant)
    begin
        rec.Get(primaryKey);
    end;

    // Busca cabeceras con filtro libre
    procedure FindSet(var rec: Record "Sales Header"; filter: Text)
    begin
        rec.SetFilter("Document Type", filter);
        rec.FindSet();
    end;
}

// ------------------------------------------------------------
// 4️⃣ UnitOfWork (control transaccional)
// ------------------------------------------------------------
codeunit 50102 "Business Central UnitOfWork"
{
    var
        // Repositorios que la unidad de trabajo controla
        SalesHeaderRepo : Codeunit "SalesHeader Repository";
        // Se pueden añadir más repositorios (Customer, Item, etc.)

        // Savepoint para rollback parcial (si se desea)
        SavePointId : Text[30];

    // Abre una transacción y crea un savepoint
    procedure Begin()
    begin
        // Inicia la transacción implícita del servidor
        // y guarda un punto de retorno
        SavePointId := 'UOW_' + Format(CurrentDateTime, 0, '<Year><Month><Day><Hour><Minute><Second>');
        Savepoint(SavePointId);
    end;

    // Confirma todos los cambios
    procedure Commit()
    begin
        Commit(); // Commit implícito del servidor
    end;

    // Revierte a la última llamada a Begin()
    procedure Rollback()
    begin
        // Si ocurre alguna excepción, volver al savepoint
        Rollback(SavePointId);
    end;

    // Exposición de los repositorios (solo lectura)
    procedure GetSalesHeaderRepo(): Codeunit "SalesHeader Repository"
    begin
        exit(SalesHeaderRepo);
    end;
}
