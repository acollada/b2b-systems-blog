# Diseño de Webhooks seguros para sincronización de datos entre sistemas

Los webhooks son una forma ligera y eficiente de comunicar eventos entre sistemas. Cuando se usan para sincronizar datos, la seguridad debe ser una prioridad, pues los endpoints reciben información sensible y pueden ser blanco de ataques.  
Este artículo detalla un **enfoque completo** para diseñar, implementar y mantener webhooks seguros, con énfasis en la sincronización de datos entre aplicaciones.

---

## 1. Requisitos previos y contexto técnico

| Tema | Descripción |
|------|-------------|
| **Conocimientos de HTTP/HTTPS** | Entender los verbos, códigos de estado, cabeceras, y el modelo de cliente‑servidor. |
| **TLS/SSL** | Los webhooks deben expedirse sobre HTTPS para proteger la confidencialidad e integridad de la información. |
| **Autenticación y autorización** | Usar tokens, HMAC, OAuth 2.0, o mecanismos propios para validar que la llamada proviene del remitente correcto. |
| **Idempotencia** | Evitar la duplicación de eventos. Se suele usar un *idempotency‑key* o un identificador de evento único. |
| **Mecanismo de reintento** | El emisor debe reintentar cuando el receptor devuelve códigos de error 5xx o 429. |
| **Registro y auditoría** | Persistir logs de eventos recibidos, respuestas, y métricas de rendimiento. |
| **Gestión de secretos** | Almacenar claves o tokens en un almacén seguro (KMS, Vault, etc.) y rotarlos periódicamente. |
| **Escalabilidad y concurrencia** | Si el volumen de eventos es alto, usar colas (RabbitMQ, SQS, Kafka) para desacoplar la recepción del procesamiento. |
| **Pruebas** | Herramientas como Postman, ngrok, o servicios de simulación de webhooks (Webhook.site, RequestBin). |

> **Nota**: Este artículo asume que ya tienes un backend funcional y que puedes crear rutas HTTP. Si no, revisa tutoriales de tu stack elegido (Node.js, Python, Go, etc.) antes de continuar.

## 2. Paso a paso de implementación con listas numeradas

1. **Planificación del esquema de datos**  
   - Define el JSON que se enviará.  
   - Incluye un identificador de evento (`event_id`) y un timestamp (`event_time`).  
   - Añade un `signature` opcional que será calculado en el emisor.

2. **Generar y almacenar secretos**  
   - Para cada cliente o servicio receptor, crea una clave secreta (`HMAC_SECRET`).  
   - Almacénala en un KMS o archivo de configuración cifrado.  
   - Registra la clave en una tabla de “webhook\_subscribers” con su URL de destino.

3. **Crear el endpoint receptor**  
   - Expone una ruta `/webhooks/<subscriber_id>` que acepte `POST`.  
   - Asegúrate de que solo acepte HTTPS.  

4. **Validar la firma**  
   - Recupera el cuerpo bruto (`raw_body`) y la cabecera `X-Hub-Signature-256`.  
   - Calcula el HMAC SHA‑256: `hmac = HMAC_SHA256(secret, raw_body)`.  
   - Compara de forma constante la firma recibida con la calculada.  
   - Si falla, responde `401 Unauthorized`.

5. **Verificar idempotencia**  
   - Extrae `event_id`.  
   - Consulta la tabla de `processed_events` para ver si ya existe.  
   - Si existe, responde `200 OK` sin procesar de nuevo.

6. **Procesar el evento**  
   - Deserializa el JSON.  
   - Ejecuta la lógica de negocio (actualizar base de datos, disparar workflows, etc.).  
   - Si el procesamiento falla, responde `500 Internal Server Error` (el emisor reintentará).

7. **Responder con éxito**  
   - Devuelve `200 OK` con un cuerpo JSON opcional (`{"status":"received"}`).  

8. **Persistir el evento**  
   - Inserta una fila en `processed_events` con `event_id`, `subscriber_id`, `status`, `timestamp`.  
   - Opcional: guarda el payload completo para auditoría.

9. **Implementar reintentos y back‑off**  
   - En el emisor, usa una política de reintento exponencial con jitter.  
   - Limita el número máximo de reintentos (ej. 5) y, si se excede, marca el evento como `failed`.

10. **Monitoreo y alertas**  
    - Métricas: tasa de eventos, tasa de errores 4xx/5xx, latencia.  
    - Alertas: tasa alta de 5xx, eventos duplicados, eventos no procesados después de X reintentos.

11. **Rotación de secretos**  
    - Programa una tarea que genere una nueva clave cada 30‑90 días.  
    - Notifica al emisor (ej. vía email o API) para que actualice la firma.

12. **Pruebas de seguridad**  
    - Usa herramientas como OWASP ZAP o Burp Suite para escanear la ruta.  
    - Verifica que la firma sea obligatoria y que la validación sea robusta contra ataques de timing.

## 3. Bloque de código de ejemplo comentado

A continuación un ejemplo en **Node.js** con **Express** y **crypto**.  
Este fragmento cubre la ruta receptor, la validación de firma, idempotencia y respuesta.

```js
// webhook-receiver.js
const express = require('express');
const crypto = require('crypto');
const bodyParser = require('body-parser');
const { getSecret, isEventProcessed, markEventProcessed } = require('./db'); // funciones de acceso a BD

const app = express();

/* 1. Usamos bodyParser.raw para obtener el cuerpo bruto (necesario para HMAC) */
app.use(bodyParser.raw({ type: '*/*' }));

/* 2. Ruta de webhook: /webhooks/:subscriberId */
app.post('/webhooks/:subscriberId', async (req, res) => {
  const { subscriberId } = req.params;
  const rawBody = req.body; // Buffer

  /* 3. Recuperar la clave secreta del subscriber */
  const secret = await getSecret(subscriberId);
  if (!secret) return res.status(404).send('Subscriber not found');

  /* 4. Calcular HMAC SHA-256 */
  const hmac = crypto
    .createHmac('sha256', secret)
    .update(rawBody)
    .digest('hex');

  /* 5. Obtener firma enviada por el emisor */
  const receivedSignature = req.headers['x-hub-signature-256'];
  if (!receivedSignature) return res.status(401).send('Missing signature');

  /* 6. Comparar firmas de forma constante */
  const signaturesMatch = crypto.timingSafeEqual(
    Buffer.from(hmac, 'hex'),
    Buffer.from(receivedSignature.replace('sha256=', ''), 'hex')
  );

  if (!signaturesMatch) return res.status(401).send('Invalid signature');

  /* 7. Parsear JSON */
  let payload;
  try {
    payload = JSON.parse(rawBody.toString());
  } catch (e) {
    return res.status(400).send('Invalid JSON');
  }

  const { event_id: eventId, event_type, data } = payload;

  /* 8. Idempotencia: verificar si ya se procesó */
  if (await isEventProcessed(subscriberId, eventId)) {
    // Evento ya manejado, responder OK sin repetir lógica
    return res.status(200).send('Already processed');
  }

  try {
    /* 9. Procesar el evento (ejemplo: actualizar BD) */
    await processEvent(event_type, data);

    /* 10. Marcar como procesado */
    await markEventProcessed(subscriberId, eventId, 'success');

    res.status(200).send('Event received');
  } catch (err) {
    /* 11. Si falla, marcar como error y permitir reintentos */
    await markEventProcessed(subscriberId, eventId, 'failed', err.message);
    res.status(500).send('Processing error');
  }
});

/* 12. Iniciar servidor */
const PORT = process.env.PORT || 3000;
app.listen(PORT, () => console.log(`Webhook receiver listening on ${PORT}`));
```

### Comentarios clave

- **`bodyParser.raw`**: Es esencial para obtener el cuerpo sin parsear, ya que la firma se calcula sobre los bytes originales.
- **Firma HMAC SHA‑256**: Se recomienda usar SHA‑256 en vez de SHA‑1 por su mayor seguridad.
- **`crypto.timingSafeEqual`**: Evita ataques de timing que podrían revelar la firma correcta.
- **Idempotencia**: Garantiza que un mismo `event_id` no se procese dos veces, incluso si el emisor reintenta.
- **Manejo de errores**: Se devuelve `500` para que el emisor lo reintente, y se registra el error para auditoría.

## 4. Buenas prácticas y errores comunes a evitar

| Buenas prácticas | Por qué | Errores comunes |
|------------------|---------|-----------------|
| **HTTPS obligatorio** | Evita MITM y garantiza confidencialidad. | Usar HTTP en producción. |
| **Firmas HMAC** | Verifica la integridad y autenticidad. | No firmar, o usar firmas débiles (MD5, SHA‑1). |
| **Comparación constante** | Previene ataques de timing. | Comparar strings con `===`. |
| **Idempotencia** | Evita duplicados y estados inconsistentes. | Procesar cada POST sin verificar. |
| **Manejo de reintentos** | Aumenta la confiabilidad de la sincronización. | No responder con códigos 5xx cuando falla. |
| **Rotación de secretos** | Reduce el impacto de una clave comprometida. | Dejar claves estáticas indefinidamente. |
| **Validación de payload** | Evita ataques de inyección o payloads inesperados. | No validar esquema JSON. |
| **Rate‑limiting** | Protege contra DoS y abuso. | No limitar la frecuencia de llamadas. |
| **Registro exhaustivo** | Facilita auditoría y depuración. | No persistir eventos ni errores. |
| **Separar procesamiento** | Evita cuellos de botella y permite escalabilidad. | Ejecutar lógica de negocio dentro de la ruta. |
| **Escalabilidad con colas** | Permite desacoplar recepción y procesamiento. | Procesar directamente sin colas. |
| **Pruebas de seguridad** | Detecta vulnerabilidades antes de producción. | No probar con herramientas de escaneo. |
| **Métricas y alertas** | Permite detectar fallos rápidamente. | No monitorizar la tasa de errores. |
| **Documentación** | Facilita la integración de clientes. | Falta de especificaciones claras. |

### Errores comunes a evitar

| Nº | Error | Impacto | Solución |
|----|-------|---------|----------|
| 1 | No usar TLS | Intercepción de datos, ataques MITM. | Forzar HTTPS, renovar certificados. |

| 3 | No validar `event_id` | Duplicados, sobreescritura de datos. | Registrar y comprobar idempotencia. |
