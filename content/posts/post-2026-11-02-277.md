# Optimización de consultas SQL y gestión de índices en ERPs B2B

Los ERP (Enterprise Resource Planning) que operan en un entorno B2B suelen manejar miles de transacciones por segundo, integrando datos de ventas, compras, inventarios, finanzas y logística. Cuando el volumen crece, la eficiencia de las consultas SQL se vuelve crítica: un mal diseño de índices o una consulta no optimizada puede degradar el rendimiento de todo el sistema, provocar cuellos de botella y afectar la experiencia del cliente.  
En este artículo se describe un proceso sistemático para optimizar consultas y gestionar índices en bases de datos de ERPs B2B, con énfasis en bases de datos relacionales comunes (SQL Server, Oracle, PostgreSQL y MySQL).

> **Objetivo**:  
> - Identificar consultas críticas.  
> - Diseñar e implementar índices adecuados.  
> - Mantener estadísticas y estructuras de índices actualizadas.  
> - Establecer buenas prácticas y evitar errores comunes.

---

## 1. Requisitos previos y contexto técnico

| Tema | Detalles |
|------|----------|
| **Tipo de base de datos** | SQL Server (Transact‑SQL), Oracle (PL/SQL), PostgreSQL (PL/pgSQL), MySQL (InnoDB). |
| **Arquitectura** | OLTP (procesamiento de transacciones) + OLAP (reportes y análisis). |
| **Datos** | Tablas de 10 M a 500 M registros, con índices en PK, FK y columnas de búsqueda. |
| **Carga de trabajo** | Transacciones concurrentes (creación, actualización, borrado) + consultas de lectura intensiva (reportes, dashboards). |
| **Herramientas de monitoreo** | DMVs (SQL Server), V$SQL y V$SQL_PLAN (Oracle), pg_stat_statements (PostgreSQL), Performance Schema (MySQL). |
| **Requisitos de SLA** | Tiempo de respuesta < 2 s para 95 % de las consultas de lectura. |
| **Equipo** | DBA, analista de rendimiento, desarrollador de ERP, arquitecto de datos. |

### 1.1. Entorno B2B y particularidades

1. **Multi‑tenant**: datos de múltiples clientes en una sola base de datos.  
2. **Transacciones de alto volumen**: cada operación puede generar 3‑5 índices a actualizar.  
3. **Regulaciones**: cumplimiento de GDPR, PCI‑DSS, etc. → auditoría de índices y consultas.  
4. **Escalabilidad horizontal**: sharding o particiones de tablas para distribuir la carga.

## 2. Paso a paso de implementación con listas numeradas

> **Nota**: Los pasos siguientes se pueden adaptar a cualquier RDBMS; se incluyen comandos específicos de SQL Server como referencia, pero la lógica es aplicable a Oracle, PostgreSQL y MySQL.

### 2.1. 1. Análisis de la carga de trabajo

1. **Recopilar métricas de uso**  
   - `SELECT * FROM sys.dm_exec_query_stats;` (SQL Server)  
   - `SELECT * FROM v$sql;` (Oracle)  
   - `SELECT * FROM pg_stat_statements;` (PostgreSQL)  
   - `SELECT * FROM performance_schema.events_statements_summary_by_digest;` (MySQL)

2. **Identificar consultas con mayor frecuencia y/o mayor tiempo**  
   - Ordenar por `total_worker_time` (SQL Server) o `elapsed_time` (Oracle).  
   - Generar un reporte con las 20 consultas más costosas.

3. **Definir métricas objetivo**  
   - Tiempo de respuesta, CPU, I/O, número de filas devueltas.

### 2.2. 2. Identificación de consultas críticas

1. **Revisar planes de ejecución**  
   - `SET STATISTICS IO ON; SET STATISTICS TIME ON;` (SQL Server)  
   - `EXPLAIN ANALYZE` (PostgreSQL)  
   - `AUTOTRACE` (Oracle)  

2. **Detectar operaciones costosas**  
   - Escaneos completos de tabla (Table Scan).  
   - Índices no utilizados (Index Scan sin filtro).  
   - Joins de alto costo (Nested Loops vs Hash Join).

3. **Documentar**  
   - Guardar el texto de la consulta y el plan de ejecución en un ticket de mejora.

### 2.3. 3. Revisión de planes de ejecución

1. **Analizar cardinalidad**  
   - Verificar si la estimación de filas coincide con la realidad.  
   - Ajustar `SET STATISTICS IO ON` y comparar con el plan.

2. **Detectar estadísticas obsoletas**  
   - `SELECT * FROM sys.dm_db_stats_properties('dbo.MiTabla', 1);` (SQL Server).  
   - En Oracle: `DBMS_STATS.CHECK_DATABASE_STATS`.  

3. **Actualizar estadísticas**  
   ```sql
   UPDATE STATISTICS dbo.MiTabla WITH FULLSCAN;   -- SQL Server
   EXEC DBMS_STATS.GATHER_TABLE_STATS('SCHEMA', 'MI_TABLA');  -- Oracle
   ```

### 2.4. 4. Diseño de índices

| Consideración | Acción | Ejemplo |
|---------------|--------|---------|
| **Selección de columnas** | Índices compuestos que reflejen filtros y ordenamiento | `CREATE INDEX IX_ORDERS_CUST_DATE ON Orders(CustomerID, OrderDate);` |
| **Filtrado de índices** | Índices filtrados para columnas con valores raros | `CREATE INDEX IX_INVENTORY_LOW ON Inventory(ProductID) WHERE Quantity < 10;` (SQL Server) |
| **Columna de búsqueda** | Índices sobre columnas de búsqueda frecuente (LIKE, IN) | `CREATE INDEX IX_CUSTOMERS_NAME ON Customers(Name);` |
| **Evitar columnas no usadas** | Revisar consultas para eliminar columnas no referenciadas | `DROP INDEX IX_ORDERS_UNNEEDED;` |
| **Índices de unión** | Índices sobre claves foráneas | `CREATE INDEX IX_OrderDetails_OrderID ON OrderDetails(OrderID);` |

#### 2.4.1. Índices compuestos vs. simples

- **Índice compuesto**: útil cuando las consultas filtran por varias columnas en el mismo orden.  
- **Índice simple**: más ligero, pero puede ser insuficiente si la consulta usa varias columnas.

#### 2.4.2. Índices filtrados (SQL Server) / Índices parciales (PostgreSQL)

- Reducen el tamaño del índice y la sobrecarga de mantenimiento.

#### 2.4.3. Índices de columnas calculadas

- Si la consulta usa una expresión, crear una columna calculada y luego indexarla.

### 2.5. 5. Implementación y pruebas

1. **Crear índices en entorno de pruebas**  
   - Ejecutar `CREATE INDEX` en la base de datos de staging.  
   - Ejecutar el conjunto de pruebas de carga.

2. **Comparar métricas**  
   - Medir tiempo de respuesta, CPU, I/O antes y después.  
   - Validar que el rendimiento mejora y que no hay regresiones.

3. **Validar integridad**  
   - Verificar que las restricciones de integridad no se rompen.  
   - Confirmar que los triggers y procedimientos almacenados siguen funcionando.

### 2.6. 6. Automatización de mantenimiento

| Acción | Herramienta | Script de ejemplo |
|--------|-------------|-------------------|
| **Reorganizar índices** | SQL Server `ALTER INDEX ... REORGANIZE` | `ALTER INDEX ALL ON dbo.MiTabla REORGANIZE;` |
| **Reconstruir índices** | SQL Server `ALTER INDEX ... REBUILD` | `ALTER INDEX IX_ORDERS_CUST_DATE ON dbo.Orders REBUILD;` |
| **Actualizar estadísticas** | SQL Server `UPDATE STATISTICS` | `UPDATE STATISTICS dbo.MiTabla;` |
| **Programar jobs** | SQL Server Agent, Oracle Scheduler, cron (PostgreSQL) | `CREATE OR REPLACE JOB mi_job RECURRING 0 0 2 * * * EXECUTE PROCEDURE actualizar_stats();` |

### 2.7. 7. Monitoreo continuo y ajuste

1. **Dashboards de rendimiento**  
   - Grafana + Prometheus (PostgreSQL)  
   - Power BI (SQL Server)  
   - Oracle Enterprise Manager

2. **Alertas**  
   - CPU > 80 % por > 5 min.  
   - Tiempo de respuesta > 2 s para más del 10 % de las consultas.  

3. **Revisión periódica**  
   - Cada 3 meses revisar índices obsoletos, estadísticas y patrones de consulta.  
   - Ajustar o eliminar índices que no se usan.

## 3. Bloque de código de ejemplo comentado

```sql
/* ==========================================================
   Ejemplo completo de optimización en SQL Server
   ========================================================== */

-- 1. Identificar la consulta más costosa
SELECT TOP 10
    qs.last_execution_time,
    qs.execution_count,
    qs.total_worker_time,
    qs.total_elapsed_time,
    qt.text AS sql_text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
ORDER BY qs.total_worker_time DESC;

-- 2. Obtener el plan de ejecución
SET SHOWPLAN_XML ON;  -- Habilita la salida XML del plan
GO
SELECT * FROM sys.dm_exec_sql_text(@sql_handle);  -- Reemplazar @sql_handle
GO
SET SHOWPLAN_XML OFF;

-- 3. Crear un índice compuesto que cubra la consulta
CREATE INDEX IX_ORDERS_CUST_DATE
ON dbo.Orders (CustomerID, OrderDate DESC)
INCLUDE (OrderTotal, Status);

-- 4. Actualizar estadísticas de la tabla
UPDATE STATISTICS dbo.Orders WITH FULLSCAN;

-- 5. Reorganizar índices fragmentados > 30%
ALTER INDEX ALL ON dbo.Orders REORGANIZE;

-- 6. Programa de mantenimiento (job)
EXEC msdb.dbo.sp_add_job
    @job_name = N'Maintenance_Orders';

EXEC msdb.dbo.sp_add_jobstep
    @job_name = N'Maintenance_Orders',
    @step_name = N'Rebuild Indexes',
    @subsystem = N'TSQL',
    @command = N'ALTER INDEX ALL ON dbo.Orders REBUILD WITH (FILLFACTOR = 80);',
    @retry_attempts = 1,
    @retry_interval = 5;

EXEC msdb.dbo.sp_add_schedule
    @schedule_name = N'Daily_Maintenance',
    @freq_type = 4,          -- Daily
    @freq_interval = 1,
    @active_start_time = 020000;  -- 02:00 AM

EXEC msdb.dbo.sp_attach_schedule
    @job_name = N'Maintenance_Orders',
    @schedule_name = N'Daily_Maintenance';
```

> **Comentarios**  
> - La consulta en el paso 1 muestra las 10 más costosas.  
> - En el paso 3 se crea un índice que incluye columnas de proyección (`OrderTotal`, `Status`) para evitar un *bookmark lookup*.  
> - El `UPDATE STATISTICS WITH FULLSCAN` fuerza una actualización completa; en producción se suele usar `RESAMPLE` o `AUTOGATHER`.  
> - El job de mantenimiento se ejecuta a las 02:00 AM, fuera de horas pico.
