# Diseño de Webhooks seguros para sincronización de datos entre sistemas

> *Webhooks* son una forma ligera y eficiente de comunicar eventos entre aplicaciones. Cuando la comunicación implica la transferencia de datos sensibles o críticos, la seguridad se vuelve esencial. En este artículo se explica cómo diseñar, implementar y mantener webhooks seguros, centrándose en la sincronización de datos entre sistemas.

> **Enfoque**:  
> - Autenticación y autorización  
> - Integridad y confidencialidad de la carga útil  
> - Resiliencia y escalabilidad  
> - Pruebas y monitoreo

---

## 1. Requisitos previos y contexto técnico

| Tema | Descripción | Herramientas / Tecnologías comunes |
|------|-------------|------------------------------------|
| **Arquitectura de eventos** | Sistema A envía un *payload* a un endpoint de Sistema B cuando ocurre un evento. | RESTful, HTTP/HTTPS, JSON |
| **Formato de datos** | JSON es el estándar, pero se puede usar XML, Protobuf, etc. | `application/json` |
| **Canal de comunicación** | HTTP/HTTPS, websockets, AMQP (para sistemas internos) | `curl`, `Postman`, `nginx`, `haproxy` |
| **Autenticación** | Tokens, HMAC, certificados TLS, OAuth 2.0 | `JWT`, `openssl`, `nginx auth_request` |
| **Cifrado** | TLS 1.2+ para la capa transport, opcionalmente cifrado de payload | TLS, AES-GCM |
| **Reintentos y idempotencia** | Manejo de errores y duplicados | `Retry-After`, `Idempotency-Key` |
| **Registro y monitoreo** | Logs, métricas, alertas | ELK, Prometheus, Grafana, CloudWatch |

> **Nota**: Este artículo asume que ambos sistemas están en la nube y que el endpoint de recepción está expuesto a Internet. Si los sistemas están dentro de la misma red, se pueden aplicar medidas adicionales como VPN o VPC peering.

## 2. Paso a paso de implementación con listas numeradas

> **Objetivo**: Crear un webhook que envíe una notificación de “nuevo registro” desde *Sistema A* a *Sistema B* y que sea seguro, confiable e idempotente.

### 2.1. Preparación del entorno

1. **Generar certificados TLS**  
   ```bash
   openssl req -newkey rsa:2048 -nodes -keyout webhook.key -x509 -days 365 -out webhook.crt
   ```
   - Instalar `webhook.crt` y `webhook.key` en el servidor que recibirá las peticiones.

2. **Crear una clave secreta compartida** (para HMAC)  
   ```bash
   # En ambos sistemas, generar la misma clave de 32 bytes
   openssl rand -hex 32 > shared_secret.txt
   ```

3. **Registrar la URL del webhook** en el sistema receptor (Sistema B).  
   - Ejemplo: `https://api.sistemab.com/webhooks/receive`

### 2.2. Envío del webhook (Sistema A)

1. **Construir la carga útil** (payload).  
   ```json
   {
     "event": "user.created",
     "timestamp": "2024-11-03T12:34:56Z",
     "data": {
       "user_id": 12345,
       "email": "ejemplo@dominio.com"
     }
   }
   ```

2. **Calcular el HMAC** (SHA‑256) con la clave secreta.  
   ```bash
   echo -n '<payload>' | openssl dgst -sha256 -hmac '<shared_secret>' -binary | base64
   ```

3. **Enviar la petición POST** con cabeceras de seguridad.  
   ```bash
   curl -X POST https://api.sistemab.com/webhooks/receive \
        -H "Content-Type: application/json" \
        -H "X-Webhook-Signature: <hmac_base64>" \
        -H "X-Webhook-Event: user.created" \
        -H "X-Webhook-Timestamp: 2024-11-03T12:34:56Z" \
        -H "Authorization: Bearer <jwt_token>" \
        --cert webhook.crt --key webhook.key \
        -d '<payload>'
   ```

4. **Manejo de reintentos**  
   - Si la respuesta no es `2xx`, volver a enviar después de `Retry-After` (si está presente) o con backoff exponencial.

### 2.3. Recepción y validación (Sistema B)

1. **Validar TLS** (el servidor ya está configurado con `webhook.crt`/`webhook.key`).

2. **Verificar la firma**  
   - Recalcular HMAC con la carga útil y comparar con `X-Webhook-Signature`.  
   - Si no coinciden → rechazar con `401 Unauthorized`.

3. **Validar la autenticación**  
   - Decodificar el JWT en `Authorization`.  
   - Verificar issuer, audience, expiration, y firma.  
   - Si falla → `401 Unauthorized`.

4. **Validar el timestamp**  
   - Comprobar que el `X-Webhook-Timestamp` no sea demasiado viejo (ej.: > 5 minutos).  
   - Si es viejo → `403 Forbidden`.

5. **Procesar el evento**  
   - Usar `event` para dirigir la lógica.  
   - Registrar el `Idempotency-Key` (si se envía) para evitar duplicados.

6. **Responder con `200 OK`** una vez procesado satisfactoriamente.

## 3. Bloque de código de ejemplo comentado

```python
# webhook_receiver.py
import hmac
import hashlib
import json
import time
from flask import Flask, request, abort, jsonify

app = Flask(__name__)

# Clave secreta compartida (en producción, usar variables de entorno)
SHARED_SECRET = b"0123456789abcdef0123456789abcdef"

# Función auxiliar para validar HMAC
def verify_signature(payload: bytes, signature: str) -> bool:
    """Calcula HMAC SHA256 y compara con la firma recibida."""
    computed = hmac.new(SHARED_SECRET, payload, hashlib.sha256).hexdigest()
    return hmac.compare_digest(computed, signature)

# Middleware de validación
@app.before_request
def validate_webhook():
    # 1. Verificar encabezados obligatorios
    required_headers = ["X-Webhook-Signature", "X-Webhook-Event", "X-Webhook-Timestamp"]
    for h in required_headers:
        if h not in request.headers:
            abort(400, description=f"Missing header {h}")

    # 2. Verificar firma
    payload = request.get_data()
    signature = request.headers["X-Webhook-Signature"]
    if not verify_signature(payload, signature):
        abort(401, description="Invalid signature")

    # 3. Validar timestamp (máximo 5 minutos de diferencia)
    ts = request.headers["X-Webhook-Timestamp"]
    try:
        ts_epoch = time.mktime(time.strptime(ts, "%Y-%m-%dT%H:%M:%SZ"))
    except ValueError:
        abort(400, description="Invalid timestamp format")
    if abs(time.time() - ts_epoch) > 5 * 60:
        abort(403, description="Timestamp out of range")

    # 4. (Opcional) Validar JWT en Authorization
    # ...

@app.route("/webhooks/receive", methods=["POST"])
def receive_webhook():
    data = request.get_json()
    event = request.headers["X-Webhook-Event"]

    # Procesar según tipo de evento
    if event == "user.created":
        user_id = data["data"]["user_id"]
        email = data["data"]["email"]
        # Aquí se haría la lógica de sincronización
        print(f"Nuevo usuario {user_id} ({email}) sincronizado.")

    # Responder 200 OK
    return jsonify({"status": "ok"}), 200

if __name__ == "__main__":
    # Ejecutar con TLS en producción
    app.run(host="0.0.0.0", port=443, ssl_context=("webhook.crt", "webhook.key"))
```

### Comentarios clave

- **HMAC**: Se usa `compare_digest` para evitar ataques de timing.
- **Timestamp**: Previene replay attacks.
- **Flask `before_request`**: Centraliza la validación.
- **TLS**: Se habilita en el servidor, garantizando confidencialidad en tránsito.

## 4. Buenas prácticas y errores comunes a evitar

| Área | Buenas prácticas | Errores comunes |
|------|------------------|-----------------|
| **Autenticación** | - Usar JWT con firma RSA/ECDSA.<br>- Incluir `iss`, `aud`, `exp` en el token.<br>- Rotar claves regularmente. | - Usar tokens estáticos sin expiración.<br>- No validar la firma. |
| **Integridad** | - Firmar la carga útil completa (payload + headers).<br>- Usar HMAC SHA‑256 o SHA‑384. | - Firmar solo el payload sin incluir headers.<br>- Comparar firmas con `==` en vez de `compare_digest`. |
| **Confidencialidad** | - Forzar HTTPS con TLS 1.2+.<br>- Configurar ciphers fuertes (ECDHE‑RSA‑AES‑256-GCM). | - Permitir TLS 1.0/1.1.<br>- No revocar certificados caducados. |
| **Idempotencia** | - Incluir `Idempotency-Key` en cada petición.<br>- Almacenar claves procesadas con TTL. | - Procesar duplicados (p.ej., reintentos sin idempotencia). |
| **Reintentos** | - Usar backoff exponencial.<br>- Responder con `Retry-After`. | - Reintentos infinitos sin límite.<br>- No respetar `Retry-After`. |
| **Validación de timestamp** | - Limitar ventana a 5–10 minutos.<br>- Ajustar a UTC. | - Permitir timestamps arbitrarios (vulnerabilidad de replay). |
| **Escalabilidad** | - Usar colas (RabbitMQ, SQS) para decoupling.<br>- Escalar horizontalmente el endpoint. | - Procesar todo síncronamente, bloqueando la cola. |
| **Monitoreo** | - Registrar métricas de latencia, tasa de fallos.<br>- Alertar en `4xx` y `5xx`. | - No monitorear, dejando fallos sin detección. |
| **Pruebas** | - Unit tests para firmas y validaciones.<br>- Test de replay y reintentos. | - No probar casos de borde (timestamps viejos, firmas corruptas). |

### Checklist rápido

1. **TLS**: Certificado válido, revocado y actualizado.  
2. **Firma**: HMAC + headers, `compare_digest`.  
3. **JWT**: Firmado, expira, verifica `iss`/`aud`.  
4. **Timestamp**: UTC, ventana ≤ 5 min.  
5. **Idempotencia**: Clave única, TTL.  
6. **Reintentos**: Backoff exponencial, `Retry-After`.  
7. **Logging**: Payload hash, evento, estado.  
8. **Alertas**: Tasa de fallos > 5 % → alarma.

## Conclusión

Diseñar webhooks seguros implica combinar varias capas de protección: TLS para la capa de transporte, HMAC para la integridad, JWT para la autenticación, y mecanismos de idempotencia y reintentos para la confiabilidad. Siguiendo los pasos y buenas prácticas descritos, podrás construir un mecanismo de sincronización de datos robusto y resiliente, minimizando el riesgo de ataques y fallos operativos.
