# Optimización de consultas SQL y gestión de índices en ERPs B2B

> **Nota**: Este artículo está pensado para desarrolladores, DBA y arquitectos de sistemas que trabajan con ERP (Enterprise Resource Planning) orientados a B2B (Business‑to‑Business). Se cubren los conceptos esenciales, la configuración paso‑a‑paso y las buenas prácticas que garantizan un rendimiento sólido en entornos con grandes volúmenes de datos y transacciones simultáneas.

---

## 1. Requisitos previos y contexto técnico

| Elemento | Descripción | Herramientas / Tecnologías |
|----------|-------------|---------------------------|
| **Base de datos** | Relacional, con soporte para índices, particiones y estadísticas. Ejemplos: PostgreSQL, MySQL 8+, Microsoft SQL Server, Oracle 19c. | `psql`, `mysql`, `sqlcmd`, `sqlplus` |
| **ERP B2B** | Sistema que gestiona ventas, compras, inventarios, facturación y logística entre empresas. Requiere alta concurrencia y consistencia ACID. | SAP Business One, Microsoft Dynamics 365, Odoo, custom ERP |
| **Carga de trabajo** | Lecturas de catálogo de productos, consultas de órdenes, generación de reportes de fin de mes, conciliaciones contables. | Carga de 10k‑100k filas por tabla, 200+ concurrentes |
| **Herramientas de monitoreo** | `EXPLAIN`, `EXPLAIN ANALYZE`, `pg_stat_statements`, `SHOW STATUS LIKE 'Innodb%';` | `pgAdmin`, `MySQL Workbench`, `SQL Server Management Studio` |
| **Entorno de prueba** | Base de datos con datos de producción simulada (50‑70 % de la tabla real). | `pgbench`, `mysqldump`, scripts de carga de datos |
| **Política de backups** | Snapshots y copias incrementales. | `pg_basebackup`, `mysqldump`, `SQL Server Backup` |
| **Equipo** | DBA, desarrollador de ERP, analista de negocio. | 3‑5 personas en un sprint de 2‑4 semanas |

> **Objetivo**: Reducir el tiempo de respuesta de consultas críticas en 30‑50 % y minimizar el impacto de la carga de índices en el rendimiento de escritura.

---

## 2. Paso a paso de implementación con listas numeradas

1. **Análisis de la carga actual**  
   1.1. Ejecuta `EXPLAIN (ANALYZE, BUFFERS)` en las consultas más frecuentes.  
   1.2. Identifica planes con `Seq Scan` en tablas grandes.  
   1.3. Registra los `wait_event` y `I/O` en los logs de la base de datos.  
   1.4. Prioriza las consultas que consumen > 5 s o > 20 % de CPU.

2. **Recolección de estadísticas**  
   2.1. Ejecuta `ANALYZE` en cada tabla o `VACUUM ANALYZE` en PostgreSQL.  
   2.2. En MySQL, ejecuta `ANALYZE TABLE`.  
   2.3. Asegúrate de que la frecuencia de actualización sea > 1 hora en entornos de alta inserción.

3. **Definición de índices “candidatos”**  
   3.1. Para cada consulta, extrae las columnas de `WHERE`, `JOIN`, `ORDER BY` y `GROUP BY`.  
   3.2. Evalúa la cardinalidad: columnas con < 5 % de valores únicos no suelen beneficiarse de índices.  
   3.3. Prioriza índices compuestos que cubran la mayoría de los filtros.  
   3.4. Si la tabla es de alta escritura, considera índices “column-store” o “covering” para evitar lecturas adicionales.

4. **Creación de índices en modo “offline”**  
   4.1. Usa `CREATE INDEX CONCURRENTLY` en PostgreSQL o `CREATE INDEX` con `LOCK=NONE` en MySQL.  
   4.2. Si el ERP no permite bloqueos, ejecuta en ventana de mantenimiento (p.ej. 02:00‑04:00).  
   4.3. Verifica el espacio ocupado: `pg_relation_size()` o `information_schema.tables`.

5. **Evaluación de rendimiento**  
   5.1. Repite `EXPLAIN ANALYZE` y compara tiempos.  
   5.2. Ejecuta pruebas de carga con `pgbench` o `sysbench` y verifica la latencia de escritura.  
   5.3. Ajusta la configuración de la base de datos (buffers, cache, autovacuum).

6. **Optimización de consultas**  
   6.1. Refactoriza SQL: elimina `SELECT *`, usa `JOIN` explícitos, evita subconsultas anidadas innecesarias.  
   6.2. Aplica `WITH (NOLOCK)` en SQL Server o `READ UNCOMMITTED` en MySQL cuando sea aceptable.  
   6.3. Si el ERP permite vistas materializadas, crea una vista que pre‑agregue datos de ventas por cliente.

7. **Revisión de particiones**  
   7.1. Si la tabla supera 10 M filas, considera particiones por rango (`year`, `month`) o hash (`customer_id`).  
   7.2. En PostgreSQL, usa `CREATE TABLE … PARTITION BY RANGE`.  
   7.3. Actualiza los índices para cada partición.

8. **Automatización y monitorización**  
   8.1. Programa `ANALYZE` y `VACUUM` en cron o en el scheduler del RDBMS.  
   8.2. Configura alertas de `slow query log`.  
   8.3. Implementa dashboards con Grafana + Prometheus o CloudWatch (para RDS).

9. **Documentación y control de cambios**  
   9.1. Registra cada índice creado en el repositorio de scripts de infraestructura.  
   9.2. Añade notas en la documentación de la base de datos con la justificación y el impacto esperado.  
   9.3. Realiza revisiones de código con el equipo de DBA y desarrollo.

10. **Revisión final**  
    10.1. Ejecuta pruebas de regresión: asegura que la funcionalidad del ERP no se vea afectada.  
    10.2. Valida que las transacciones de alta concurrencia siguen siendo consistentes.  
    10.3. Documenta el “before‑after” de los tiempos de respuesta para presentar a stakeholders.

## 3. Bloque de código de ejemplo comentado

```sql
-- 1. Tabla de ventas en un ERP B2B (simplificada)
CREATE TABLE sales_order (
    order_id      BIGINT PRIMARY KEY,
    customer_id   BIGINT NOT NULL,
    product_id    BIGINT NOT NULL,
    order_date    DATE NOT NULL,
    quantity      INT NOT NULL,
    unit_price    NUMERIC(10,2) NOT NULL,
    status        VARCHAR(20) NOT NULL,
    CONSTRAINT fk_customer FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id),
    CONSTRAINT fk_product FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);

-- 2. Índice compuesto para consultas de reporte mensual por cliente
CREATE INDEX idx_sales_order_customer_date
    ON sales_order (customer_id, order_date);

-- 3. Índice único para asegurar la unicidad de una orden por cliente y producto
CREATE UNIQUE INDEX uq_sales_order_customer_product
    ON sales_order (customer_id, product_id, order_date);

-- 4. Consulta de reporte: Ventas por cliente en un rango de fechas
SELECT
    so.customer_id,
    SUM(so.quantity * so.unit_price) AS total_sales
FROM
    sales_order so
WHERE
    so.order_date BETWEEN '2024-01-01' AND '2024-01-31'
    AND so.status = 'COMPLETED'
GROUP BY
    so.customer_id
ORDER BY
    total_sales DESC;

-- 5. Explicación del plan de ejecución (PostgreSQL)
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    so.customer_id,
    SUM(so.quantity * so.unit_price) AS total_sales
FROM
    sales_order so
WHERE
    so.order_date BETWEEN '2024-01-01' AND '2024-01-31'
    AND so.status = 'COMPLETED'
GROUP BY
    so.customer_id
ORDER BY
    total_sales DESC;
```

**Comentarios clave**

- El índice `idx_sales_order_customer_date` permite un *index scan* eficiente cuando filtramos por rango de fechas y cliente.  
- El índice único evita duplicados y mejora la velocidad de inserción en tablas con alta concurrencia.  
- La consulta usa `SUM` y `GROUP BY` sobre la columna `customer_id`; gracias al índice compuesto, el planner puede usar un *bitmap index scan* seguido de un *hash aggregate* rápido.  
- El `EXPLAIN ANALYZE` muestra los buffers leídos y el tiempo de CPU; si el plan sigue siendo un *Seq Scan*, revisa la cardinalidad o añade un índice en `status`.

## 4. Buenas prácticas y errores comunes a evitar

| Buenas prácticas | Por qué funcionan | Errores comunes |
|------------------|-------------------|-----------------|
| **Usar índices compuestos** | Reduce la cantidad de índices y cubre múltiples filtros en una sola búsqueda. | Crear índices individuales en cada columna de `WHERE` sin considerar la cardinalidad. |
| **Mantener estadísticas actualizadas** | El optimizador necesita datos reales para elegir el plan correcto. | Ignorar `ANALYZE` después de grandes cargas; usar `autovacuum` con intervalos muy largos. |
| **Evitar `SELECT *`** | Reduce la cantidad de datos transferidos y mejora la caché de la base. | Consultas que retornan más columnas de las necesarias, provocando lecturas innecesarias. |
| **Usar particiones en tablas muy grandes** | Permite eliminar rápidamente particiones completas y reduce el número de páginas escaneadas. | Particionar sin planificar la estrategia de partición, causando fragmentación y sobre‑indexación. |
| **Revisar el impacto de índices en escrituras** | Cada índice adicional añade overhead a `INSERT`, `UPDATE`, `DELETE`. | Crear índices sin analizar su coste en transacciones de alta frecuencia. |
| **Implementar “covering indexes”** | Si el índice contiene todas las columnas usadas en la consulta, el planner puede evitar acceder a la tabla. | Dependencia de la tabla para leer columnas que podrían estar en el índice. |
| **Monitorizar `slow query log`** | Detecta rápidamente consultas que cambian de rendimiento después de actualizaciones. | Ignorar logs de lentitud; asumir que la base de datos siempre está óptima. |
| **Planificar pruebas de carga** | Verifica el comportamiento bajo concurrencia real. | Testar solo con una sesión; subestimar el efecto de bloqueo y contenido de recursos. |
| **Documentar cada cambio** | Facilita la reversión y la auditoría de rendimiento. | Cambios “in‑place” sin registro; dificulta la trazabilidad. |

---

### Resumen

Optimizar consultas SQL y gestionar índices en ERPs B2B es un proceso iterativo que combina análisis de carga, estadísticas actualizadas, índices bien diseñados y pruebas de rendimiento. Siguiendo los pasos descritos y evitando los errores comunes, podrás lograr mejoras sustanciales en la velocidad de respuesta y en la eficiencia de la escritura, garantizando que el ERP siga siendo escalable y fiable para los procesos críticos de negocio.
