# Gestión de errores de concurrencia y bloqueos de tabla en bases de datos corporativas  

> **Objetivo**: Proporcionar una guía práctica y profunda sobre cómo identificar, diagnosticar y resolver problemas de concurrencia y bloqueo de tablas en entornos de bases de datos corporativas (SQL Server, Oracle, MySQL, PostgreSQL).  

> **Audiencia**: Administradores de bases de datos (DBA), arquitectos de datos, desarrolladores de aplicaciones y analistas de rendimiento.  

---

## 1. Requisitos previos y contexto técnico  

| Tema | Descripción | Requisitos |
|------|-------------|------------|
| **Transacciones y aislamiento** | Entender los niveles de aislamiento (`READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`, `READ UNCOMMITTED`) y su impacto en los bloqueos. | Conocimientos básicos de ACID. |
| **Bloqueo de recursos** | Diferenciar bloqueos de línea vs bloqueos de tabla, bloqueos compartidos (S) vs exclusivos (X). | Familiaridad con la semántica de bloqueo de su SGBD. |
| **Deadlocks** | Comprender cómo se forman, detectan y resuelven los deadlocks. | Conocimiento de `WAITFOR` en SQL Server, `SELECT FOR UPDATE` en Oracle, `SELECT ... LOCK IN SHARE MODE` en MySQL. |
| **Escalado de bloqueos** | Saber cuándo y por qué un SGBD escala bloqueos de línea a tabla. | Experiencia con `sp_lock` (SQL Server), `DBA_BLOCKERS` (Oracle). |
| **Optimistic vs Pessimistic locking** | Seleccionar la estrategia adecuada según el patrón de acceso. | Conocimiento de versiones de fila (`ROWVERSION`/`TIMESTAMP`), `SELECT FOR UPDATE SKIP LOCKED`. |
| **Herramientas de diagnóstico** | `SQL Server Profiler`, `sys.dm_tran_locks`, `DBA_HIST_ACTIVE_SESS_HISTORY` (Oracle), `SHOW PROCESSLIST` (MySQL), `pg_locks` (PostgreSQL). | Acceso a herramientas y privilegios de DBA. |
| **Patrones de concurrencia** | Uso de transacciones cortas, índices adecuados, particionamiento. | Buenas prácticas de diseño de esquema. |

> **Nota**: El contenido está pensado para bases de datos corporativas con alta concurrencia (millones de transacciones diarias). Los ejemplos se centran en SQL Server y Oracle, pero los conceptos se aplican a cualquier SGBD relacional.

## 2. Paso a paso de implementación con listas numeradas  

1. **Identificar los patrones de acceso**  
   1.1. Analiza los scripts de producción y el código de la aplicación.  
   1.2. Revisa los índices y su cobertura.  
   1.3. Determina si las transacciones son largas o cortas.  

2. **Seleccionar el nivel de aislamiento adecuado**  
   2.1. Si la aplicación puede tolerar lecturas sucias, usa `READ UNCOMMITTED`.  
   2.2. Para evitar lecturas sucias y no repetir lecturas, usa `REPEATABLE READ`.  
   2.3. En entornos críticos, considera `SERIALIZABLE`.  

3. **Implementar bloqueo optimista cuando sea posible**  
   3.1. Añade una columna `row_version` (`TIMESTAMP`/`ROWVERSION`).  
   3.2. En la actualización, verifica la versión de la fila:  
   ```sql
   UPDATE tabla SET valor = @nuevoValor
   WHERE id = @id AND row_version = @rowVersionAnterior;
   IF @@ROWCOUNT = 0
       RAISEERROR('Optimistic lock failure', 16, 1);
   ```  

4. **Usar bloqueos explícitos en transacciones críticas**  
   4.1. En SQL Server: `SELECT ... FROM tabla WITH (UPDLOCK, ROWLOCK)`.  
   4.2. En Oracle: `SELECT ... FOR UPDATE`.  
   4.3. En MySQL: `SELECT ... FOR UPDATE`.  

5. **Prevenir deadlocks con orden de adquisición de recursos**  
   5.1. Establece un orden fijo de acceso a tablas (`tablaA → tablaB → tablaC`).  
   5.2. Evita `SELECT *` que pueda escanear tablas completas.  

6. **Implementar timeouts y reintentos**  
   6.1. En SQL Server: `SET LOCK_TIMEOUT 5000;` (5 s).  
   6.2. En Oracle: `ALTER SESSION SET DDL_LOCK_TIMEOUT = 5;` (5 s).  
   6.3. En MySQL: `SET innodb_lock_wait_timeout = 5;`  

7. **Monitorear bloqueos y deadlocks**  
   7.1. SQL Server:  
   ```sql
   SELECT * FROM sys.dm_tran_locks;
   SELECT * FROM sys.dm_os_waiting_tasks;
   ```  
   7.2. Oracle:  
   ```sql
   SELECT * FROM v$session_blocking_info;
   ```  
   7.3. PostgreSQL:  
   ```sql
   SELECT * FROM pg_locks;
   ```  

8. **Optimizar índices y consultas**  
   8.1. Asegúrate de que los índices cubran los `WHERE` y `JOIN`.  
   8.2. Evita `SELECT *` y `ORDER BY` sin índices.  

9. **Escalar a particiones o sharding**  
   9.1. Si una tabla recibe millones de actualizaciones, partición por rango o hash.  
   9.2. Reducir la contención de bloqueos a nivel de partición.  

10. **Revisar y ajustar la configuración del SGBD**  
    10.1. `max degree of parallelism` en SQL Server.  
    10.2. `lock_timeout` en Oracle y MySQL.  
    10.3. `deadlock_timeout` en PostgreSQL.

## 3. Bloque de código de ejemplo comentado  

A continuación, un ejemplo completo en **SQL Server** que ilustra la gestión de concurrencia con bloqueo optimista y manejo de deadlocks:

```sql
/* ------------------------------------------------------------------
   Ejemplo: Gestión de concurrencia con bloqueo optimista y manejo de
   deadlocks en SQL Server
   ------------------------------------------------------------------ */

/* 1. Crear tabla con columna de versión */
CREATE TABLE dbo.Pedidos (
    PedidoID      INT PRIMARY KEY,
    ClienteID     INT NOT NULL,
    Estado        VARCHAR(20) NOT NULL,
    FechaCreado   DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    FechaActualiza DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    RowVer        ROWVERSION NOT NULL   -- columna de versión automática
);

/* 2. Insertar datos de prueba */
INSERT INTO dbo.Pedidos (PedidoID, ClienteID, Estado)
VALUES (1, 101, 'Pendiente'),
       (2, 102, 'Pendiente');

/* 3. Procedimiento de actualización con bloqueo optimista */
CREATE OR ALTER PROCEDURE dbo.ActualizarEstadoPedido
    @PedidoID      INT,
    @NuevoEstado   VARCHAR(20),
    @RowVerPrevio  BINARY(8)  -- valor de RowVer leído previamente
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRY
        /* 3.1. Intentar actualizar solo si la versión coincide */
        UPDATE dbo.Pedidos
        SET Estado = @NuevoEstado,
            FechaActualiza = SYSUTCDATETIME()
        WHERE PedidoID = @PedidoID
          AND RowVer = @RowVerPrevio;

        IF @@ROWCOUNT = 0
        BEGIN
            /* 3.2. Si no se actualizó, lanzar error de conflicto */
            THROW 50001, 'Conflicto de concurrencia: la fila fue modificada por otro proceso.', 1;
        END
    END TRY
    BEGIN CATCH
        /* 3.3. Capturar y propagar error */
        DECLARE @ErrMsg NVARCHAR(4000) = ERROR_MESSAGE();
        THROW 50002, @ErrMsg, 1;
    END CATCH
END
GO

/* 4. Ejemplo de uso con manejo de reintentos */
DECLARE @PedidoID INT = 1,
        @NuevoEstado VARCHAR(20) = 'Procesado',
        @RowVerPrevio BINARY(8),
        @RetryCount INT = 0,
        @MaxRetries INT = 3;

-- Obtener la versión actual
SELECT @RowVerPrevio = RowVer FROM dbo.Pedidos WHERE PedidoID = @PedidoID;

WHILE @RetryCount < @MaxRetries
BEGIN
    BEGIN TRY
        EXEC dbo.ActualizarEstadoPedido
            @PedidoID,
            @NuevoEstado,
            @RowVerPrevio;
        PRINT 'Actualización exitosa.';
        BREAK;   -- salir del bucle si tiene éxito
    END TRY
    BEGIN CATCH
        /* 5.1. Si el error es de concurrencia, intentar de nuevo */
        IF ERROR_NUMBER() = 50001
        BEGIN
            SET @RetryCount = @RetryCount + 1;
            PRINT CONCAT('Reintento ', @RetryCount, ' por conflicto de concurrencia.');
            /* Obtener la nueva versión antes de reintentar */
            SELECT @RowVerPrevio = RowVer FROM dbo.Pedidos WHERE PedidoID = @PedidoID;
        END
        ELSE
        BEGIN
            /* 5.2. Otros errores: lanzar y salir */
            THROW;
        END
    END CATCH
END

IF @RetryCount = @MaxRetries
    PRINT 'Error: se alcanzó el número máximo de reintentos.';
```

### Comentarios clave  

| Línea | Comentario |
|-------|------------|
| `RowVer ROWVERSION` | SGBD asigna automáticamente un valor único que cambia en cada actualización. |
| `UPDATE ... WHERE RowVer = @RowVerPrevio` | Garantiza que la fila no haya cambiado desde que la leímos. |
| `THROW 50001` | Código de error personalizado para conflicto de concurrencia. |
| `TRY/CATCH` | Permite capturar y reaccionar a errores específicos. |
| `@RetryCount` | Implementa reintentos automáticos para evitar que el usuario final experimente fallos. |
| `SELECT @RowVerPrevio = RowVer` | Actualiza la versión antes de cada reintento. |

## 4. Buenas prácticas y errores comunes a evitar  

### Buenas prácticas  

| Área | Recomendación | Por qué |
|------|---------------|---------|
| **Transacciones cortas** | Mantener las transacciones tan breves como sea posible. | Reduce el tiempo de bloqueo y la posibilidad de deadlocks. |
| **Índices adecuados** | Crear índices que cubran los `WHERE` y `JOIN`. | Evita escaneos de tabla completos que generan bloqueos de tabla. |
| **Orden de acceso** | Acceder a tablas en el mismo orden en todas las transacciones. | Previene ciclos de espera que provocan deadlocks. |
| **Bloqueo explícito controlado** | Usar hints (`UPDLOCK`, `ROWLOCK`) solo cuando sea necesario. | Evita bloqueos de tabla innecesarios. |
| **Timeouts razonables** | Configurar `LOCK_TIMEOUT`/`innodb_lock_wait_timeout` a valores que permitan reintentos sin frustrar al usuario. | Evita esperas indefinidas. |
| **Reintentos con back‑off exponencial** | Cuando se detecta un conflicto, esperar 100‑500 ms antes de reintentar. | Reduce la contención y mejora la distribución de carga. |
| **Monitoreo continuo** | Automatizar alertas sobre `waits` de bloqueo y `deadlocks`. | Detectar problemas antes de que afecten a producción. |
| **Particionamiento** | Dividir tablas grandes por rango o hash. | Reduce la contención de bloqueos a nivel de partición. |
| **Uso de versiones de fila** | Cuando sea posible, usar `ROWVERSION`/`TIMESTAMP`. | Facilita la detección de conflictos sin bloquear. |
| **Evitar SELECT * en transacciones** | Seleccionar solo columnas necesarias. | Minimiza la cantidad de datos bloqueados. |

### Errores comunes a evitar  

| Error | Impacto | Cómo evitarlo |
|-------|---------|---------------|
| **Bloqueo de tabla completo** | Alta contención, rendimiento caído. | Usar `ROWLOCK`, índices y particiones. |
| **Transacciones largas** | Mayor probabilidad de deadlocks y bloqueos. | Refactorizar lógica para transacciones cortas. |
| **Ignorar niveles de aislamiento** | Lecturas sucias, inconsistencias. | Ajustar nivel de aislamiento según la necesidad. |
| **No manejar deadlocks** | Aplicación falla sin explicación
