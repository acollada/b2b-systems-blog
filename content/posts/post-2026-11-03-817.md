# Gestión de errores de concurrencia y bloqueos de tabla en bases de datos corporativas  

La concurrencia y los bloqueos son dos de los retos más críticos que enfrentan los sistemas de bases de datos corporativas. Cuando varios procesos intentan leer o escribir los mismos datos al mismo tiempo, se pueden producir **deadlocks**, **esperas prolongadas** o incluso **perdida de datos** si la gestión de concurrencia no se realiza correctamente.  

En este artículo abordaremos de forma práctica cómo identificar, diagnosticar y resolver los errores más comunes de concurrencia y bloqueos de tabla, con ejemplos de código y buenas prácticas para entornos productivos.

---

## 1. Requisitos previos y contexto técnico

| Tema | Descripción |
|------|-------------|
| **Tipo de BD** | SQL Server, PostgreSQL o Oracle. El ejemplo se centra en SQL Server y PostgreSQL, pero la lógica es aplicable a otros RDBMS. |
| **Niveles de aislamiento** | `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE` (y variantes como `READ COMMITTED SNAPSHOT`). |
| **Bloqueos** | Bloqueo de fila (`ROWLOCK`), bloqueos de página (`PAGLOCK`), bloqueos de tabla (`TABLOCK`) y bloqueo de escalada (`LOCK_ESCALATION`). |
| **Herramientas de diagnóstico** | DMV/PGC (`sys.dm_tran_locks`, `sys.dm_os_waiting_tasks`, `pg_locks`, `pg_stat_activity`). |
| **Patrones de concurrencia** | Optimistic Concurrency Control (OCC), Pessimistic Locking, Versioning (Snapshot Isolation). |
| **Transacciones** | Uso de `BEGIN TRAN`, `COMMIT`, `ROLLBACK`, `SET TRANSACTION ISOLATION LEVEL`. |
| **Control de errores** | `TRY...CATCH` (SQL Server), `EXCEPTION` (PostgreSQL), `SAVEPOINT` y `ROLLBACK TO`. |

### 1.1 Escenario típico de una base de datos corporativa

1. **Operaciones CRUD**: Muchas transacciones simultáneas que actualizan tablas de clientes, facturación, inventario, etc.  
2. **Transacciones largas**: Operaciones de consolidación de datos, generación de reportes, ETL.  
3. **Carga variable**: picos de uso durante cierre de mes o temporada alta.  
4. **Requisitos de ACID**: Garantizar consistencia y durabilidad sin sacrificar rendimiento.

## 2. Paso a paso de implementación con listas numeradas

A continuación, se detalla un flujo de trabajo para gestionar errores de concurrencia y bloqueos de tabla de forma sistemática.

### 2.1 Diagnóstico inicial

1. **Identificar transacciones que generan bloqueos**  
   ```sql
   -- SQL Server
   SELECT 
       tl.request_session_id AS session_id,
       tl.resource_type,
       tl.resource_database_id,
       tl.resource_associated_entity_id,
       tl.request_mode,
       tl.request_status,
       t.text AS query_text
   FROM sys.dm_tran_locks AS tl
   JOIN sys.dm_exec_requests AS er ON tl.request_session_id = er.session_id
   CROSS APPLY sys.dm_exec_sql_text(er.sql_handle) AS t
   WHERE tl.request_status = 'WAITING';
   ```

2. **Obtener el plan de ejecución**  
   ```sql
   -- SQL Server
   DBCC TRACEON (1222, -1);   -- habilita el logging de deadlocks
   ```

3. **Revisar métricas de rendimiento**  
   - `pg_stat_activity` y `pg_locks` en PostgreSQL.  
   - `sys.dm_os_wait_stats` en SQL Server.

### 2.2 Ajustar el nivel de aislamiento

4. **Escoger el nivel de aislamiento adecuado**  
   - `READ COMMITTED` (predeterminado) para la mayoría de las operaciones.  
   - `SERIALIZABLE` solo cuando la consistencia estricta es crítica.  
   - `READ COMMITTED SNAPSHOT` (RCSI) en SQL Server para evitar bloqueos de lectura.

5. **Aplicar RCSI**  
   ```sql
   ALTER DATABASE [MiBaseDatos] SET READ_COMMITTED_SNAPSHOT ON;
   ```

### 2.3 Optimizar el acceso a tabla

6. **Usar índices adecuados**  
   - Índices de cobertura para reducir la necesidad de bloqueos de tabla.  
   - Índices de columnas que aparecen en cláusulas `WHERE` y `JOIN`.

7. **Evitar bloqueos de tabla explícitos**  
   - No usar `TABLOCK` a menos que sea absolutamente necesario.  
   - Si se necesita, usar `TABLOCKX` solo en transacciones cortas.

8. **Escalada de bloqueos**  
   - Deshabilitar la escalada de bloqueos si la tabla es pequeña:  
     ```sql
     ALTER TABLE dbo.MiTabla SET (LOCK_ESCALATION = TABLE);
     ```

### 2.4 Implementar control de concurrencia

9. **Control de concurrencia optimista**  
   - Añadir columna `row_version` (`TIMESTAMP` o `ROWVERSION` en SQL Server, `xmin` en PostgreSQL).  
   - Verificar versión antes de `UPDATE`.  

10. **Control de concurrencia pesimista**  
    - Bloquear explícitamente filas antes de actualizar:  
      ```sql
      SELECT * FROM dbo.MiTabla WITH (UPDLOCK, ROWLOCK) WHERE id = @id;
      ```

### 2.5 Manejo de errores y reintentos

11. **Capturar errores de deadlock**  
    - SQL Server: error 1205.  
    - PostgreSQL: error 40P01.  

12. **Implementar lógica de reintentos**  
    ```sql
    DECLARE @RetryCount INT = 0;
    WHILE @RetryCount < 3
    BEGIN
        BEGIN TRY
            BEGIN TRANSACTION;
            -- Operaciones críticas
            COMMIT TRANSACTION;
            BREAK; -- éxito
        END TRY
        BEGIN CATCH
            IF ERROR_NUMBER() = 1205 -- deadlock
            BEGIN
                ROLLBACK TRANSACTION;
                SET @RetryCount = @RetryCount + 1;
                WAITFOR DELAY '00:00:01'; -- back‑off
            END
            ELSE
                THROW; -- re‑lanzar otros errores
        END CATCH
    END
    ```

### 2.6 Monitoreo y alertas

13. **Crear alertas de bloqueo**  
    - SQL Server: `SQL Server Agent` con alertas de error 1205.  
    - PostgreSQL: `pg_stat_activity` y `pg_locks` combinados con scripts de monitoreo.

14. **Dashboard de rendimiento**  
    - Visualizar métricas de espera, bloqueos y tiempo de transacción.  
    - Alertar cuando los tiempos de espera superen umbrales críticos.

## 3. Bloque de código de ejemplo comentado

A continuación, se muestra un ejemplo completo de una función que actualiza el saldo de una cuenta bancaria con control de concurrencia optimista y reintentos ante deadlocks. Se incluye la creación de la tabla, la inserción de datos y la función en SQL Server y PostgreSQL.

### 3.1 SQL Server

```sql
-- 1. Crear tabla con columna de versión
CREATE TABLE dbo.Cuentas (
    Id          INT PRIMARY KEY,
    ClienteId   INT NOT NULL,
    Saldo       DECIMAL(18,2) NOT NULL,
    RowVersion  ROWVERSION NOT NULL  -- columna de control de concurrencia
);

-- 2. Insertar datos de prueba
INSERT INTO dbo.Cuentas (Id, ClienteId, Saldo)
VALUES (1, 1001, 5000.00),
       (2, 1002, 7500.00);

-- 3. Función para transferir fondos con reintentos
CREATE OR ALTER FUNCTION dbo.TransferirFondos (
    @FromId   INT,
    @ToId     INT,
    @Monto    DECIMAL(18,2)
)
RETURNS BIT
AS
BEGIN
    DECLARE @RetryCount INT = 0;
    DECLARE @Success BIT = 0;

    WHILE @RetryCount < 3 AND @Success = 0
    BEGIN
        BEGIN TRY
            BEGIN TRANSACTION;

            -- Obtener filas con bloqueo de actualización (optimista)
            SELECT Saldo, RowVersion
            FROM dbo.Cuentas WITH (UPDLOCK, ROWLOCK)
            WHERE Id IN (@FromId, @ToId);

            -- Validar saldos
            IF EXISTS (SELECT 1 FROM dbo.Cuentas WHERE Id = @FromId AND Saldo < @Monto)
                THROW 50001, 'Saldo insuficiente', 1;

            -- Actualizar saldos
            UPDATE dbo.Cuentas
            SET Saldo = Saldo - @Monto
            WHERE Id = @FromId;

            UPDATE dbo.Cuentas
            SET Saldo = Saldo + @Monto
            WHERE Id = @ToId;

            COMMIT TRANSACTION;
            SET @Success = 1;
        END TRY
        BEGIN CATCH
            IF ERROR_NUMBER() = 1205  -- Deadlock
            BEGIN
                ROLLBACK TRANSACTION;
                SET @RetryCount = @RetryCount + 1;
                WAITFOR DELAY '00:00:01';  -- back‑off
            END
            ELSE
            BEGIN
                ROLLBACK TRANSACTION;
                THROW;  -- Re‑lanzar error
            END
        END CATCH
    END

    RETURN @Success;
END;
GO
```

**Comentarios clave**

- `ROWVERSION` actúa como marca de versión; si otra transacción cambia la fila antes de `COMMIT`, la actualización fallará.
- `UPDLOCK` + `ROWLOCK` garantizan que solo se bloqueen las filas necesarias.
- La lógica de reintentos evita que un deadlock detenga la aplicación.
- Se devuelve `BIT` indicando éxito (`1`) o fracaso (`0`).

### 3.2 PostgreSQL

```sql
-- 1. Crear tabla con columna de versión (xmin)
CREATE TABLE public.cuentas (
    id          SERIAL PRIMARY KEY,
    cliente_id  INT NOT NULL,
    saldo       NUMERIC(18,2) NOT NULL
);

-- 2. Insertar datos
INSERT INTO public.cuentas (cliente_id, saldo)
VALUES (1001, 5000.00),
       (1002, 7500.00);

-- 3. Función PL/pgSQL con reintentos
CREATE OR REPLACE FUNCTION transferir_fondos(
    p_from_id INT,
    p_to_id   INT,
    p_monto   NUMERIC
) RETURNS BOOLEAN AS $$
DECLARE
    retry_count INT := 0;
    success     BOOLEAN := FALSE;
    from_saldo  NUMERIC;
    to_saldo    NUMERIC;
BEGIN
    WHILE retry_count < 3 AND NOT success LOOP
        BEGIN
            -- Iniciar transacción explícita
            BEGIN
                -- Bloquear filas con FOR UPDATE (pessimistic)
                SELECT saldo INTO from_saldo
                FROM public.cuentas
                WHERE id = p_from_id
                FOR UPDATE;

                SELECT saldo INTO to_saldo
                FROM public.cuentas
                WHERE id = p_to_id
                FOR UPDATE;

                IF from_saldo < p_monto THEN
                    RAISE EXCEPTION 'Saldo insuficiente';
                END IF;

                -- Actualizar saldos
                UPDATE public.cuentas SET saldo = saldo - p_monto
                WHERE id = p_from_id;

                UPDATE public.cuentas SET saldo = saldo + p_monto
                WHERE id = p_to_id;

                COMMIT;
                success := TRUE;
            EXCEPTION
                WHEN deadlock_detected THEN
                    ROLLBACK;
                    retry_count := retry_count + 1;
                    PERFORM pg_sleep(1);  -- back‑off
                WHEN others THEN
                    ROLLBACK;
                    RAISE;
            END;
        END;
    END LOOP;

    RETURN success;
END;
$$ LANGUAGE plpgsql;
```

**Comentarios clave**

- En PostgreSQL, `FOR UPDATE` bloquea las filas hasta `COMMIT`.  
- Se usa `deadlock_detected` (error 40P01) para capturar deadlocks.  
- `pg_sleep` actúa como back‑off.  
- La función devuelve `TRUE` si la transferencia se realizó correctamente.
