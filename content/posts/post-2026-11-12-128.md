# Patrones de diseño y control transaccional robusto en extensiones de Business Central

El desarrollo en Microsoft Dynamics 365 Business Central (BC) ha evolucionado significativamente con la migración desde C/AL a AL. Si bien AL simplifica la sintaxis, la complejidad de la lógica de negocio y la integridad de los datos exigen un enfoque arquitectónico riguroso. Este artículo aborda la implementación de patrones de diseño sólidos y estrategias avanzadas de control transaccional para garantizar que las extensiones sean mantenibles, eficientes y seguras en entornos de alto volumen.

## 1. Requisitos previos, contexto técnico y arquitectura

Para implementar correctamente estas prácticas, el desarrollador debe tener un dominio profundo de los siguientes conceptos:

*   **Modelo de Datos de BC:** Comprensión de cómo las tablas están relacionadas mediante claves primarias y foráneas, y cómo el motor de base de datos (Azure SQL Database) gestiona los bloques de datos.
*   **Gestión de Transacciones en AL:** Diferencia entre transacciones implícitas (cada operación de base de datos es una transacción si no se especifica lo contrario) y explícitas (`BEGIN`, `COMMIT`, `ROLLBACK`).
*   **Extensibilidad:** Uso correcto de `tableextension`, `pageextension`, `codeunit` y `interface`.
*   **Principios SOLID y Clean Code:** Aplicación de responsabilidad única, abierto/cerrado y segregación de interfaces.

### Contexto Técnico y Arquitectura

En Business Central, la mayoría de los errores críticos en producción provienen de dos fuentes:
1.  **Violaciones de integridad referencial** debido a operaciones parciales (ej. se inserta la cabecera pero falla la línea).
2.  **Bloqueos de base de datos** causados por transacciones largas que bloquean otras operaciones concurrentes.

La arquitectura recomendada para extensiones robustas se basa en el **patrón de Servicio de Dominio (Domain Service Layer)**:
*   **Capa de Presentación (Pages/Reports):** Solo orquesta la UI. No contiene lógica de negocio.
*   **Capa de Servicio (Codeunits):** Contiene la lógica de negocio, validaciones y gestión de transacciones.
*   **Capa de Datos (Tables/Storage):** Interacción directa con la base de datos, minimizada y encapsulada.

## 2. Paso a paso de implementación en AL

A continuación, se detalla el proceso para implementar un control transaccional robusto utilizando un patrón de "Unit of Work" explícito y manejo de errores estructurado.

1.  **Definir la Unidad de Trabajo (Unit of Work):**
    Identifique el grupo de operaciones que deben ser atómicas. Por ejemplo, la creación de una orden de compra con sus líneas y la reserva de inventario. Todo este bloque debe fallar o completarse por completo.

2.  **Iniciar la Transacción Explícita:**
    Use `Transaction.Begin` en la capa de servicio antes de realizar las primeras operaciones de escritura en la base de datos. Establezca un mensaje de contexto claro para facilitar el diagnóstico.

3.  **Implementar Validaciones Pre-transaccionales:**
    Realice todas las validaciones de negocio *antes* de iniciar la transacción o inmediatamente después de iniciarla pero antes de modificar datos. Esto evita bloquear recursos innecesariamente si los datos son inválidos.

4.  **Ejecutar Operaciones de Datos:**
    Procese las inserciones, actualizaciones o borrados. Use métodos `Insert` o `Modify` de las tablas.

5.  **Manejo de Excepciones (Try/Catch):**
    Envuelva la lógica principal en un bloque `try...catch`. Capture las excepciones específicas de AL (como `DataItemError` o `IntegrationError`) y genéricas.

6.  **Decidir entre Commit o Rollback:**
    *   Si no hay errores: Llame a `Transaction.Commit`.
    *   Si hay un error recuperable: Registre el error y decida si es posible continuar o si debe abortar.
    *   Si hay un error fatal: Llame a `Transaction.Rollback`.

7.  **Registro de Auditoría y Logs:**
    Independientemente del resultado, registre información crítica en una tabla de log o use el sistema de eventos de BC para auditoría. Esto es crucial para el soporte post-release.

8.  **Liberar Recursos:**
    Asegúrese de que no queden referencias abiertas a registros de cliente (`CurrentRecord`) que puedan interferir con transacciones posteriores.

    Subtype = Instance;

    var
        ErrorContext: Text;

    /// <summary>
    /// Crea un ajuste de inventario completo.
    /// Este método garantiza que la cabecera y todas las líneas se creen atómicamente.
    /// </summary>
    /// <param name="LocationCode">Código de la ubicación.</param>
    /// <param name="AdjustmentLines">Tabla temporal de líneas de ajuste.</param>
    procedure CreateInventoryAdjustment(LocationCode: Code[10]; var AdjustmentLines: Record "Temp Adjustment Line"): Boolean
    var
        InventoryAdj: Record "Inventory Adjustment";
        AdjLine: Record "Inventory Adjustment Line";
        Item: Record Item;
        Location: Record Location;
        Success: Boolean;
        TransactionId: Integer;
    begin
        // 1. Validaciones Pre-transaccionales (Rápido y sin bloqueo)
        if not ValidateLocation(LocationCode) then
            exit(false);

        if AdjustmentLines.Count = 0 then
            exit(false);

        // 2. Iniciar Transacción Explícita
        // El mensaje de contexto ayuda a identificar el origen del bloqueo si falla
        TransactionId := Transaction.Begin('Creating Inventory Adjustment for Location: ' + LocationCode);

        try
            // 3. Preparar la Cabecera
            InventoryAdj.Init();
            InventoryAdj."Location Code" := LocationCode;
            InventoryAdj."Adjustment Date" := Today();
            InventoryAdj."Reason Code" := 'CORRECTION'; // Valor por defecto

            // Insertar Cabecera
            if not InventoryAdj.Insert(true) then
                Error('Failed to insert Inventory Adjustment Header. Check permissions.');

            // 4. Proceso de Líneas
            foreach AdjustmentLines in AdjustmentLines do
            begin
                // Validación de Existencia del Artículo
                if not Item.Get(AdjustmentLines."Item No.") then
                    Error('Item %1 does not exist.', AdjustmentLines."Item No.");

                // Validación de Cantidad (Negativa)
                if AdjustmentLines."Quantity" <= 0 then
                    Error('Quantity must be greater than zero for Item %1.', AdjustmentLines."Item No.");

                // Preparar Línea
                AdjLine.Init();
                AdjLine."Adjustment No." := InventoryAdj."No.";
                AdjLine."Item No." := AdjustmentLines."Item No.";
                AdjLine."Quantity" := AdjustmentLines."Quantity";
                AdjLine."Location Code" := LocationCode;
                AdjLine."Cost Amount (Actual)" := 0; // Se calculará en post-commit o vía trigger

                // Insertar Línea
                if not AdjLine.Insert(true) then
                    Error('Failed to insert line for Item %1.', AdjustmentLines."Item No.");
            end;

            // 5. Reglas de Negocio Post-Inserción (Ej: Cálculo de Costo)
            CalculateAdjustmentCosts(InventoryAdj."No.");

            // 6. Confirmar Transacción
            Transaction.Commit;
            Success := true;

        catch
            // 7. Manejo de Errores
            // Siempre que ocurra un error, debemos deshacer los cambios
            Transaction.Rollback;
            Success := false;

            // Registrar el error para auditoría
            LogError(
                'Inventory Adjustment Creation Failed',
                ErrorContext,
                CopyStr(ErrorInfo.Message(), 1, 500)
            );

            // Reformatear el error para el usuario final, ocultando detalles técnicos si es necesario
            Error(ErrorInfo.Message());
        end;

        exit(Success);
    end;
