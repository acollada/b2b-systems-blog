# Buenas prácticas de depuración de logs en entornos de producción B2B

Los entornos B2B suelen combinar micro‑servicios, contenedores, orquestación (K8s, ECS, etc.) y múltiples canales de comunicación (REST, gRPC, AMQP). La depuración de logs en producción debe ser **robusta, estructurada y segura** para cumplir con los requisitos de auditoría y SLA de los clientes empresariales.  
A continuación se presenta una guía técnica completa, con ejemplos de código y recomendaciones prácticas.

---

## 1. Requisitos previos y contexto técnico

| Tema | Detalle |
|------|---------|
| **Arquitectura** | Micro‑servicios desplegados en contenedores (Docker/K8s). Cada servicio expone un endpoint de métricas y un endpoint de logs. |
| **Herramientas** | ELK (Elasticsearch‑Logstash‑Kibana), Loki, Grafana, Prometheus, Fluent Bit/Fluentd, Graylog. |
| **Lenguajes** | Python, Node.js, Go, Java, .NET. Se muestra un ejemplo en **Python**. |
| **Seguridad** | GDPR, PCI‑DSS, SOX, ISO 27001. Los logs no deben contener datos sensibles (NIF, SSN, contraseñas). |
| **Escalabilidad** | Logs deben ser ingesta‑as‑a‑service (Kafka, Pulsar, SQS). |
| **Compliance** | Retención mínima de 6 meses, auditoría de acceso a logs. |
| **Automatización** | CI/CD pipeline que despliegue la configuración de logging y verifique la generación de logs. |

> **Nota**: En entornos B2B, la calidad de la información de logs puede ser un factor de diferenciación competitiva.

---

## 2. Paso a paso de implementación con listas numeradas

> **Objetivo**: Configurar un pipeline de logging estructurado y seguro, con rotación, retención y alertas.

1. **Define los niveles de log**  
   - `DEBUG`: Información detallada, solo en desarrollo.  
   - `INFO`: Operaciones normales y eventos de negocio.  
   - `WARN`: Situaciones anómalas que no rompen la operación.  
   - `ERROR`: Fallos que requieren atención inmediata.  
   - `FATAL`: Fallos críticos que pueden llevar a la caída del servicio.

2. **Elige un formato estructurado**  
   - JSON es el estándar para logs estructurados.  
   - Incluye campos obligatorios: `timestamp`, `level`, `service`, `trace_id`, `span_id`, `message`, `error` (si aplica).  

3. **Configura el logger en cada servicio**  
   - Usa una librería de logging que soporte JSON y propagación de contexto (p.ej. `structlog` en Python).  
   - Añade middleware para capturar `trace_id` y `span_id` (OpenTelemetry).  

4. **Centraliza la ingestión de logs**  
   - **Fluent Bit** como sidecar en cada pod (K8s).  
   - Envía los logs a **Logstash** o **Loki** vía HTTP/HTTPS.  
   - Configura filtros para enriquecer los logs (geo‑IP, host, etc.).  

5. **Implementa rotación y retención**  
   - En el pipeline central (Elasticsearch, Loki) configura `index.lifecycle` con `hot`, `warm`, `cold`, `delete`.  
   - Retención mínima de 6 meses, con backups en S3 o GCS.  

6. **Define alertas y dashboards**  
   - Usa **Prometheus** + **Grafana** para métricas de log (rate de errores, latencia de logs).  
   - Configura alertas en **Alertmanager** (Slack, PagerDuty).  

7. **Seguridad y compliance**  
   - Encripta logs en tránsito (TLS) y en reposo (encriptación de disco).  
   - Aplica políticas de IAM para limitar el acceso a los índices de logs.  
   - Realiza auditorías periódicas de logs y de quién accede a ellos.  

8. **Automatiza pruebas de logging**  
   - En el pipeline CI/CD, incluye pruebas de integración que generen logs y verifiquen su formato.  
   - Usa herramientas como **Loggly** o **Datadog** para validar que los logs llegan a la plataforma.  

9. **Documenta la política de logs**  
   - Mantén un documento vivo con los requisitos de nivel, formato, retención y procedimientos de respuesta.  
   - Actualízalo cuando cambie la arquitectura o los requisitos regulatorios.

## 3. Bloque de código de ejemplo comentado (Python + structlog + OpenTelemetry)

```python
# logger_setup.py
import logging
import structlog
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.resources import SERVICE_NAME, Resource
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter

# ------------------------------------------------------------------
# 1. Configuración de OpenTelemetry (tracing)
# ------------------------------------------------------------------
trace.set_tracer_provider(
    TracerProvider(
        resource=Resource.create({SERVICE_NAME: "payment-service"})
    )
)
tracer = trace.get_tracer(__name__)

# Exportador de trazas a stdout (puedes usar Jaeger, Zipkin, etc.)
tracer_provider = trace.get_tracer_provider()
tracer_provider.add_span_processor(
    BatchSpanProcessor(ConsoleSpanExporter())
)

# ------------------------------------------------------------------
# 2. Configuración de structlog
# ------------------------------------------------------------------
logging.basicConfig(
    format="%(message)s", stream=sys.stdout, level=logging.INFO
)

structlog.configure(
    processors=[
        structlog.processors.TimeStamper(fmt="iso"),  # timestamp en ISO‑8601
        structlog.processors.add_log_level,           # añade el nivel
        structlog.processors.JSONRenderer()           # salida JSON
    ],
    context_class=dict,
    logger_factory=structlog.stdlib.LoggerFactory(),
    wrapper_class=structlog.stdlib.BoundLogger,
    cache_logger_on_first_use=True,
)

# ------------------------------------------------------------------
# 3. Función de log con trazas
# ------------------------------------------------------------------
def process_payment(amount, currency):
    with tracer.start_as_current_span("process_payment") as span:
        # Enlaza el span con el logger
        logger = structlog.get_logger().bind(
            trace_id=span.get_span_context().trace_id,
            span_id=span.get_span_context().span_id,
        )
        logger.info("Inicio del procesamiento", amount=amount, currency=currency)
        try:
            # Simulamos lógica de negocio
            if amount <= 0:
                raise ValueError("Monto inválido")
            # ...
            logger.info("Pago procesado con éxito", transaction_id="12345")
        except Exception as exc:
            # El error se captura y se envía al logger
            logger.error("Error al procesar pago", exc_info=exc)
            span.set_status(trace.status.Status(trace.status.StatusCode.ERROR, str(exc)))
            raise

# ------------------------------------------------------------------
# 4. Ejecución de ejemplo
# ------------------------------------------------------------------
if __name__ == "__main__":
    process_payment(100, "USD")
```

**Explicación rápida**

- Se crea un `TracerProvider` con `SERVICE_NAME` para que cada trace se identifique.  
- `structlog` produce logs en JSON con `timestamp`, `level`, `service`, `trace_id`, `span_id`, `message`, `error`.  
- Cada operación de negocio se envuelve en un span, lo que permite correlacionar logs y trazas.  
- Los logs se envían a stdout; en producción se redirigirían a un sidecar de Fluent Bit que los envía a Loki/ELK.

## 4. Buenas prácticas y errores comunes a evitar

### Buenas prácticas

| Área | Recomendación |
|------|---------------|
| **Formato** | Usa JSON estructurado. Evita texto plano. |
| **Propagación** | Incluye `trace_id` y `span_id` en cada log para correlación. |
| **Niveles** | Configura `DEBUG` solo en entornos de desarrollo. En producción, mínimo `INFO` o `WARN`. |
| **Contexto** | Añade contexto de negocio (e.g., `user_id`, `order_id`, `region`). |
| **Seguridad** | Nunca incluyas datos sensibles (NIF, contraseñas, tokens). Usa *redaction* o hashing. |
| **Rotación** | Configura políticas de rotación y retención desde el principio. |
| **Almacenamiento** | Elige un backend que soporte búsqueda por campos (Elasticsearch, Loki). |
| **Alertas** | Define umbrales de error y latencia. Configura alertas en Alertmanager. |
| **Testing** | Automatiza pruebas de log (formato, nivel, correlación). |
| **Documentación** | Mantén una política de logs actualizada. |

### Errores comunes a evitar

| Error | Por qué es problemático |
|-------|-------------------------|
| **Logs en texto plano** | Dificulta la búsqueda y la correlación con trazas. |
| **Niveles inconsistentes** | Los logs de `DEBUG` en producción generan ruido y consumen recursos. |
| **No usar contexto** | Los logs sin `user_id` o `transaction_id` son inútiles para depurar. |
| **No rotar logs** | Los discos se llenan y el rendimiento cae. |
| **Logs sensibles** | Riesgo de fuga de datos y sanciones regulatorias. |
| **Sin alertas** | Los errores pasan desapercibidos hasta que el cliente lo reporta. |
| **No auditar acceso** | Pérdida de trazabilidad en caso de incidentes. |

---

### Resumen

Implementar una estrategia de logging efectiva en entornos B2B de producción implica:

1. **Estructurar** los logs en JSON con trazas correlacionadas.  
2. **Centralizar** la ingestión y búsqueda.  
3. **Seguridad** y cumplimiento de normas.  
4. **Automatizar** pruebas y alertas.  

Siguiendo estos pasos y evitando los errores comunes, tu equipo podrá depurar de manera ágil, cumplir con los SLA de los clientes y mantener la confianza en los sistemas críticos.
